# 研究：画布方向几何对照（T1-11a）

> 日期：2026-09-12；对应任务卡：`../../plans/m1-recognition.md` T1-11（研究先行切片 T1-11a）。

> `../../verification/t1-10/t1-10-05-launch-page-session1.png`（3168×1440）。
> 目视对照图：[t1-11a-band-compare.png](t1-11a-band-compare.png)（上＝竖画布内容带，下＝横侧帧归一化后内容带）。
> 测量工具：`app/src/test/.../recognition/CanvasOrientationProbeTest.kt`（JVM 离线探针，可复跑）。

## 一句话结论

**两向帧之间不是旋转关系，而是「等比缩放 + 居中平移」**：横画布帧按 `竖画布宽 / 横画布宽 = 1440/3168 = 0.4545` 缩放后，
内容落在竖画布**居中**的 655 行内容带内（上留白 1256 / 下留白 1257，左右无留白），**无任何旋转**；
把横侧帧按此模型归一化后，标定模板命中位置与竖画布帧原生位置残差仅 `0,1` px（分数 0.9749 对 0.9989）。

## 1. 问题

识别产物以**竖画布标定帧（1440×3168）为唯一基准**；横画布会话（3168×1440）下帧尺寸与产物不一致，
识别全失效（T1-5 / T1-7 / T1-10 均留有实录）。方案取舍（运行时归一 / 产物多方向变体 / 坐标换算）
取决于两向帧内容的精确映射关系——纯 90° 旋转？还是带缩放 / 偏移？本切片先测量、不下结论以外的设计。

## 3. 方法（三条独立证据）

1. **内容带（留白）测量**：逐行 / 逐列像素极差定位「非均匀」区域边界——纯旋转模型下内容带应占满画布长边；
   等比缩放嵌入模型下内容带只占一段。
2. **候选模型带内比对**：对横侧帧施加 4 个候选旋转角（0°/90°/180°/270°），按「内容带对齐」重采样回竖画布几何，
   在带内与竖画布帧做逐像素相关与平均绝对差。
3. **锚点核验 + 缩放细扫**：以标定模板在归一化画布中匹配（用产物的搜索窗口，代价可控），与竖画布帧中的
   参考位置比对给出位置残差；再在带对齐缩放 ±3% 内细扫，观察锚点分数峰值位置。

## 4. 测量结果

### 证据 1：内容带（留白）

| 帧 | 内容带列 | 内容带行 | 留白 |
| --- | --- | --- | --- |
| 竖画布 1440×3168 | 0..1440（宽 1440） | 1256..1911（高 655） | 上 1256 / 下 1257 / 左 0 / 右 0 |
| 横画布侧帧 3168×1440 | 0..3168（宽 3168） | 0..1440（高 1440） | 无（整幅即内容） |

实测 `655` 与 `1256`，与期望一致（差 ≤ 1px，为整数取整）。

### 证据 2：候选模型（横侧帧 → 竖画布）

| 旋转 | 缩放 X / Y | 带内相关 | 平均绝对差 | 锚点匹配 |
| --- | --- | --- | --- | --- |
| **0°** | **2.2000 / 2.1985** | 0.3244 | 81.49 | **分数 0.9749 @651,1745** |
| 90° | 1.0000 / 4.8366 | −0.0132 | 94.45 | 0.1846 @766,1709 |
| 180° | 2.2000 / 2.1985 | −0.1627 | 100.80 | 0.2801 @669,1764 |
| 270° | 1.0000 / 4.8366 | −0.1773 | 100.35 | 0.1724 @586,1747 |

带内相关低是「两帧美术不同」所致（见口径说明）；**旋转 0° 在锚点上以 0.9749 对 ≤0.28 完胜其余三个旋转角**。

### 证据 3：锚点核验与缩放细扫

- 竖画布锚点（原生）：`651,1744`，分数 **0.9989**；归一化画布锚点：`651,1745`，分数 **0.9749** →
  **位置残差 0,1 px**（模板 131×37）。
- 缩放细扫 2.134–2.264（步 0.005）：锚点分数 0.81–0.9765，**峰值平坦**（2.184–2.209 区间均 ≥0.96），
  即单靠锚点只能把缩放定到约 ±1%；**精确比例由内容带几何确定**（`3168/1440 = 2.2` 与带高残差 ≤0.5px 一致），
  故结论以帧几何为准、不以细扫极值为准。

## 5. 结论（精确映射）

设竖画布帧 `V = (Wv, Hv) = (1440, 3168)`，横画布帧 `H = (Wh, Hh) = (3168, 1440)`（同一物理屏幕的两个方向）：

- **无旋转**：0° 是唯一成立的方向（其余三向锚点分数 ≤0.28，且纯旋转模型要求竖画布内容带占满长边，
  与实测带高 655 矛盾——两条独立证据同时排除）。
- **等比缩放，比例 = 两画布宽之比**：`k = Wv / Wh = 1440/3168 = 0.4545`（两轴一致；带高 `654.55 ≈ Wv²/Wh`）。
- **平移 = 居中留白**：`y0 = (Hv − Wv²/Wh)/2 = 1256.73`，水平平移 0。
- 映射式：`V = H · (Wv/Wh) + (0, y0)`；反解 `H = (Vx · 2.2, (Vy − 1256) · 2.2)`。
- **工程含义**：标定帧自身的**内容带**同样由帧尺寸决定——`内容带 = 居中矩形 (Wc, Wc²/Hc)`，
  本产物即 `1440×654.5 @ y0=1256.7`，与实测一致；因此「内容带」无需额外设备常量即可从帧尺寸推出。

## 6. 对 T1-11b 方案取舍的含义

1. **不需要旋转归一**：方案可以从「旋转 + 缩放 + 偏移」降级为「等比缩放 + 平移」，实现复杂度显著下降。
2. **失效机理已量化**：产物搜索窗口是「相对整幅标定帧的比例」，直接按当前帧尺寸换算会落在错误位置——
   横画布下按比例换算的窗口为 `x[1144,2009) y[776,826)`，而锚点实际在 `y≈1073`，纵向偏差约 247px
   （远超窗口高 50px）→ 必然未命中。**换算必须以「内容带」为中介，而不是整幅比例**。
3. **候选方案（供 T1-11b 定稿）**：
   - **A 运行时归一（本次数据支持，建议优先评估）**：把当前帧内容带按模型重采样到标定帧内容带几何
     （或只重采样「窗口映射到的源区域」做 ROI 归一），产物 / 阈值 / 判定语义完全不变。
     本测量已用该路径验证有效性：归一化后锚点 0.9749 远高于命中线 0.85。
   - **B 产物多方向变体**：按方向生成模板 / 窗口变体（等比缩放模板 + 换算窗口）；模板重采样方向的有效性
     本次未测（本次是「重采样帧 + 原生模板」）。
   - **C 坐标换算（只换窗口，不换帧）**：B 的轻量版，成本最低，但需明确模板缩放后的分数可比性。
   - **D 固定画布方向（已评估否决，2026-09-12）**：既然游戏恒横屏，就在采集层把画布固定为横屏尺寸，
     从根上消掉「两向不一致」。否决理由三条：
     ① **红线 4**：写死 `3168×1440` 属设备绑定常量；即便改为「按显示实时尺寸导出长边 / 短边」的合法写法，
     也仍要靠「游戏恒横屏」这一未在全场景验证的假设，把「两向都可能失效」换成「只服务横屏、竖屏必失效」，
     与 T1-11 目标（不依赖环境、两向都对）相反；
     ② **成本反向**：横画布内容满幅（不经 0.4545 缩小），同一界面标志的模板 / 搜索窗口像素面积 ×4.84
     （131×37→288×81；393×111→865×244），匹配量约 ×23（NFR-01 已是 16 倍超标）；
     ③ **需重标定**：产物 `frame` 维度变化，既有固定批次与指标报告（均在竖画布帧上）回归需重建。
     反过来说：**竖画布「缩小嵌入」的形态反而把识别成本压到 1/23**，是当前性能下更划算的运行形态。
   取舍判据：判定语义不变（对判定起作用的分数仍全精度）、零设备绑定（内容带由帧尺寸导出或标定记录）、
   增量成本（A ≈ 一次 ROI 重采样；B/C ≈ 模板重采样；D 会否决前两条并带来重标定）。
4. **阈值口径不变**：归一化后锚点分数 0.9749（对比竖画布原生 0.9989）仍远高于命中线 0.85，
   说明重采样带来的分数衰减（≈2.4%）不触及判定语义。

- **横侧输入是 adb 截屏，不是横画布采集会话帧**：本次以既有取证截图代替；真机横画布会话样本（3168×1440）

- 样本仅覆盖「启动页」一个界面，「内容带 = 居中等比嵌入」的模型只在本设备 / 本游戏两个方向各 1 例上验证；
  跨设备、跨应用、以及「画布尺寸既非标定帧也非其转置」的一般情形未验证。
- 「内容带」检测方法（逐行 / 列极差）对**自身均匀**的界面可能失效；方案落地时需给出更稳的判据，
  或在标定产物中记录标定时的内容带（T1-11b 决定）。
- 下一步：T1-11b 方案定稿（以第 6 节为输入）→ T1-11c 实现与单测 → T1-11d 双方向真机核对。

## 8. 机制补充：画布尺寸从哪来、与截图什么关系

**代码锚点**（`CaptureService.startSession`，建会话那一刻读一次）：

```156:159:app/src/main/java/com/example/mastermechanic/service/CaptureService.kt
        val metrics = resources.displayMetrics
        val width = metrics.widthPixels
        val height = metrics.heightPixels
        val densityDpi = metrics.densityDpi
```

该尺寸随后同时用于 `ImageReader.newInstance(width, height, …)` 与
`createVirtualDisplay(name, width, height, densityDpi, …)`；全库检索 `onConfigurationChanged` /
`DisplayListener` / 旋转重设 VirtualDisplay **零命中** → **画布尺寸在一个会话内冻结**。
运行期每 10s 的「帧管线统计…最近帧 WxH」即该会话画布尺寸的取证（会话内不会变）。

**用户实验（2026-09-12）**：游戏前台时，无论是否开启竖屏锁定，**截图尺寸恒为 3168×1440**。
说明「游戏前台 → 显示方向为横」与用户的锁定设置无关（应用请求优先于用户锁定）；
但这只反映**截屏那一刻的显示方向**，不等于**已建立会话的画布尺寸**。

| 情形 | 截图尺寸 | 画布尺寸 | 画布内容 |
| --- | --- | --- | --- |
| 建会话时刻与截屏时刻方向一致 | 与画布相同 | = 建会话那一刻的显示尺寸 | 满幅（一一对应） |
| 会话早已建立（如 MM 竖屏前台），之后显示转向横屏 | 3168×1440（跟随显示） | 1440×3168（冻结） | 横屏内容等比缩放 0.4545 + 居中，上下留白（本文件证据 1） |

**三层的区分**（最常被混淆的一点）：

| 层 | 尺寸由什么决定 | 游戏前台时的取值 | 会话内会变吗 |
| --- | --- | --- | --- |
| ① 游戏自身窗口 / 画面 | 游戏声明的方向（横屏）+ 当前显示 | 横屏满幅 3168×1440 | 随它自己前台 / 后台切换而变；后台通常停止渲染（单应用共享下不可见时空白化，见 T1-2） |
| ② 显示（= adb 截图） | 当前显示方向 | 3168×1440 | 跟随方向 |
| ③ 采集画布（VirtualDisplay） | 建会话那一刻的显示尺寸 | 可能是 1440×3168（更早建会话）或 3168×1440 | **不变**（冻结） |

识别看到的**不是**①，而是「① 被按 ③ 的几何等比缩放 + 居中嵌入」的结果：竖画布下等于把游戏画面缩到 **45%**
（内容带 1440×655、模板 131×37）；横画布下才是原生分辨率（模板 288×81，但匹配量 ≈×23，见第 6 节候选 D）。
游戏自身的**内部渲染分辨率**与 ① 的窗口尺寸是两回事，无法从采集数据推断，也不影响识别（识别只看到画布像素）。

**运行期告警的读法**（`CaptureService.processFrame`，每会话仅一次）：

```
帧尺寸 <运行帧 WxH> 与标定产物记录 <产物 WxH> 不一致，识别结果可能不可用
```

前一个数是**当前运行画布**，后一个数是**标定产物记录的画布**（calib-v1 为 1440×3168）。
出现这条即表示「建会话那一刻的显示方向与标定时不同」——典型触发是系统授权弹窗默认「共享一个应用」、
选王者荣耀后系统自动把游戏带回前台（横屏）→ 服务读到的显示尺寸是 3168×1440。
此时产物模板（131×37，按竖画布 45% 缩小后的像素）在满幅横画布上达不到命中线 0.85 → 判未命中、
状态持续「未知」→ 零点击（FR-08 不静默失败 + 红线 7）；规避手段为「回 MM 竖屏前台重建会话」。

**「标定时的方向」具体指什么**：指**标定那次采集会话建立那一刻**的显示方向所决定的画布尺寸
（calib-v1 为 1440×3168）；不是在框选标志或保存产物时才定的。产物里的 `frame=` 只是把**标注帧的尺寸**记下来
（T1-5l 前为 `CalibrationDraft.toData(frameWidth, frameHeight)`，现为 `writeSignalFromSelection` 取标注帧解码尺寸，语义一致：「取自当前标注帧」），而标注帧是那次会话帧池里的样本，
尺寸自然等于该会话画布。所以「运行方向 ≠ 标定方向」本质是**两次会话建立时机的差异**——告警就是拿运行帧尺寸与
产物 `frame` 字段直接比对。

该字段按设计**只记录、不参与换算**（`CalibrationData.frameWidth` 注释），窗口则存成**相对标定帧的比例**
（`SelectionWindow` 除以标定帧宽高），运行时再按**运行帧尺寸**换算回像素（`SearchWindow.pixelBounds`）——
一旦运行画布不是同一个，比例被套到错误的画布几何上，位置直接错位（第 6 节量化：纵向偏约 247px）。
**这就是当前无法自动补偿的根本原因，也是 T1-11 要补的一环**（让方向 / 内容带真正进入换算）。
操作口径：标定与运行须**同方向**建会话（现有流程靠「MM 竖屏前台建会话」保证）；换方向即需重新标定。

**判据**：要判「当前是横画布还是竖画布」，只能看**建会话那一刻**的条件或运行日志的「最近帧」，
**不能看截图**——截图只预告「此刻若建会话会得到什么画布」。
现有两向实录与本机制一致：MM 竖屏前台授权 → 画布 1440×3168（T1-5）；游戏前台授权 → 画布 3168×1440
（T1-7 / T1-10d 环境事实，两处均同时告警「帧尺寸与标定产物不一致」）。

## 9. 边界形态：会话首帧的「画布过渡帧」（旋转满幅）

**现象**（2026-09-12 用户观察，档案复核确认）：某些会话录制的**第一帧**里，游戏内容被 **90° 旋转后满幅铺满**
整幅画布（无留白），后续帧才回到「缩小嵌入」的稳定形态。

**归档证据**（三张帧尺寸都是 1440×3168 —— 画布没变，变的是内容）：

| 帧 | 来源 | 形态 | PNG 体积 |
| --- | --- | --- | --- |
| [t1-11a-transition-frame.png](../samples/t1-11a-transition-frame.png) | 旧批 idx0（`frame-0002906631593`） | **旋转满幅**（内容 90° 旋转、铺满画布） | 4037 KB |
| `replay-work/probe/frame-0002904119831.png` | 更早会话 idx0（探针取样自索引 0） | 同形态 | 4397 KB |
| `replay-work/all-batch1-43f/frame-0002906634760.png` | 同会话下一帧 | 缩小嵌入（稳定形态，正常归类 positive 且模板命中） | 760 KB |

注：旧批 idx0 此前已在 `notes-old-batch.md` 标注为「**形态A 画布过渡帧**」并排除出固定批次
（对应 samples-index set-20260912-03 的「排除 1 帧画布过渡帧」）——本次只是把机制补全。

**机制**：画布尺寸不变（始终 1440×3168），变的是**进入画布的那一瞬屏幕正处于转屏过程**：
游戏进前台时，系统先把横屏窗口以 90° 旋转铺进竖屏显示（或显示尚未完成旋转），该瞬画面被镜像进画布
→ 旋转满幅；转屏完成后才成为「横屏内容等比缩放居中嵌入」的稳定形态。

**为什么会「旋转铺满」而不是「缩小加边」——三个方向旋钮**：

| 旋钮 | 谁决定 | 变化时机 |
| --- | --- | --- |
| ① 应用请求的方向 | 游戏自己声明 landscape | 游戏进前台即生效（窗口按横屏创建 / 布局） |
| ② 显示旋转（display rotation） | 系统按顶层应用请求决策（用户锁定可覆盖；本机实测游戏请求胜出） | **异步**：WMC 决策 → relayout → display 配置变更 → 合成器重建，有几百毫秒延迟 |
| ③ 采集画布尺寸 / 旋转 | 建会话那一刻的显示尺寸（本文件第 8 节） | 会话内冻结，**不随 ①② 变化** |

① 与 ② 在转屏过渡里短暂不一致，合成器必须把应用窗口的 buffer 摆进当时的显示坐标系。**系统的默认策略是
「旋转」而不是「缩放」**：旋转是 1:1 像素变换（不损失画面、不缩小可用区域），缩放加边只在无法旋转时才用。
于是那一瞬就是「横屏窗口被 90° 旋转铺满竖屏」，被镜像进画布即为旋转满幅首帧。
而 ③ 是**固定尺寸的镜像面**（不能旋转），它的尺寸与来源显示不一致时只能走缩放 + 居中 —— 这正是稳定形态的
0.4545 缩小嵌入。两个「旋转 / 缩放」发生在不同层，不要混为一谈。

**归属仍有几种可能**（两张首帧不足以区分，待真机判定）：(i) 屏幕层 —— 当时显示还没转完，游戏被旋转呈现；
(ii) 采集层 —— 显示已转，但镜像面在那一刻仍带旧的旋转元数据；(iii) 转屏动画的中间帧 —— 系统转屏时会用
「旋转前的画面快照」做旋转 / 缩放过渡，过渡中的合成结果同样是「旋转过的旧画面」。
判定办法：采集开始的瞬间同时执行 `adb exec-out screencap -p` 与
`adb shell dumpsys display | Select-String rotation`——若截图也是竖屏（1440×3168）且游戏呈旋转态，则为屏幕层。

**对 T1-11 的含义（已写入 T1-11b 取舍输入）**：

1. **不构成误报风险**：90° 旋转内容与标定模板的 NCC 显著下降 → 判未命中；且状态机「进入需连续 2 次命中」
   （§2.2 滞回）天然过滤单帧异常。
2. **实现需显式处理**：帧尺寸与标定帧相同、但「内容带 ≈ 整幅」即为过渡 / 异常形态 → 建议跳过、判未识别；
   若归一化方案含「多方向变体」（候选 B/C），必须避免把过渡帧当成某个合法方向而给出位置语义。
3. **样本口径**：过渡帧应在批次中排除（现状已如此），或录制时跳过会话起始若干帧。

## 10. 方案定稿与实现（T1-11b / T1-11c，2026-09-12）

**定稿**：候选 A「**按画面区的运行时归一**」——不改采集画布，识别前把运行帧按画面区摆回标定几何
（决策与取舍见 [ADR-007](../../decisions/ADR-007-画布方向适配.md)）。未选：B 产物多方向变体、
C 只换算窗口、D 采集层固定画布、会话内重建 VirtualDisplay（理由见 ADR 备选方案表与本文第 6 节）。

**实现**（纯逻辑 + 平台接线，全部零设备常量）：
