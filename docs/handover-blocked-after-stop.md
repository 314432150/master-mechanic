## 1. 现象（用户视角）

1. 点「只拜访」→ 跑号走到第 8 步，打开好友列表；
2. **关闭好友列表**（用户口径：**点左半屏非列表区域**）；
3. **停止流程**；
4. 在农场页面**重新点「只拜访」** → **弹出「现在停在『好友列表』」并中断流程**；
5. 用户补充：**等一段时间（十几秒）后再点就正常了**。

用户强调过两点，都成立：
- **不是"没重新识别"**，但他确实看到"瞬间弹出"；
- 之前反馈过"你（AI）点得太慢" —— **间隔太长会掩盖问题**（见第 4 节）。

## 2. 复现路径（实测可复现）

**用 adb 完整复现（坐标均为 3168×1440 横屏下的屏幕坐标）：**

| 步骤 | 命令 |
| --- | --- |
| 打开菜单 | `input tap 3122 376`（手柄中心） |
| 点「只拜访」 | `input tap 2825 319` |
| 等它推进 | `sleep 11` |
| 关闭好友列表 | `input tap 700 700`（左半屏空白） |
| 再开菜单 | `input tap 3122 376` |
| 点「停止」 | `input tap 2800 670`（有流程时菜单底部整行） |
| **约 3 秒后**再开菜单 + 点「只拜访」 | `input tap 3122 376` → `input tap 2825 319` |

**关键**：第 7 步与第 6 步的间隔**必须短**（约 3 秒）。间隔 12 秒就复现不出来 ——
这是用户先发现的（"是不是你点太慢了"）。

## 4. 已排除（逐条查证，都**不是**原因）

| 嫌疑 | 查证结果 |
| --- | --- |
| 状态机要求"被搜过"才算未命中 | 否。`UiStateMachine.update` 里 `currentMissStreak` 只看 `current in hits` |
| 农场标志太弱 | 否。`farm_friends` 恒 **0.996~0.998（MATCHED）** |
| 「好友列表标志在农场画面上误命中」 | **否（用户亲自证伪）**：该标志是"农作物拿取提醒"文字，关掉列表后农场不出现；若互串应**永远**停在好友列表，不会十几秒后自愈。数据也支持：农场上它只有 0.10~0.15（NOT_MATCHED） |
| 我与用户先后怀疑："采集帧与真实屏幕脱节／转屏后 ImageReader 尺寸没跟上" | **已作废**：① 帧池里是**标定用的录制帧**，不是实时帧，不能当证据；② **竖屏采集是既定设计**（点击时做坐标换算），"上下黑边"是等比缩放居中的预期表现 |
| 「停止」没生效 | 曾修过一次（真有 bug，见第 5 节①），但修完症状仍在 |
| OCR 拖慢帧线程 | 真有（`窗口 24070ms / 处理 11 帧`），已修（见第 5 节②），症状仍在 |

## 5. 已实施的 4 处修复（**症状未改善**）

> 四层叠加后仍被拦，说明**根因推断仍不完全对**。接手时不要假设"已经修好了"。
> **2026-09-22 结论（§9）**：这 4 处都不是本 bug 的根因；其中 ②③④ 各有独立价值（**勿回退**），
> 但**都"轮不到执行"** —— 帧线程被一轮模板匹配整段占住了 23 秒。

① **`PatrolSession` 代次（generation）**：`stop()` / `start()` 递增，`commit(next, expectedGeneration)`
   代次不符即作废 —— 修掉"帧线程拿停止前的快照写回 ⇒ 流程复活"（曾有 `停止` 后 17 秒
   又冒出 `第 8 步通过 → 第 9 步` 的实录）。
② **OCR 节流 + 超时下调**：`MlKitNameReader.timeoutMs` 3s→1s；
   `CaptureService.OCR_MIN_INTERVAL_MS = 1000`，间隔内复用上次结果。
③ **`stepPatrol` 在 `current == null` 时直接 return**（不再把 null 喂给 `PatrolRunner.onRound`）。
④ **静止兜底重放**：`scheduleIdleRound()`（每 `IDLE_ROUND_INTERVAL_MS = 1000ms`）用
   **最近一帧像素副本**再跑一轮识别；并把"留最新画面"提到**节流判断之前**
   （`cacheLatestPixels` + `PIXEL_CACHE_INTERVAL_MS = 300`）。
   —— 心跳日志已确认它在跑（`静止兜底心跳：第 N 次（已重放）`），**但症状仍在**。

**相关文件**：
- `app/src/main/java/com/example/mastermechanic/service/CaptureService.kt`（帧管线、兜底、OCR 节流）
- `app/src/main/java/com/example/mastermechanic/patrol/PatrolSession.kt`（代次）

## 9. 真因（2026-09-22 第 5 次排查，本轮）

**§3.2 那 23 秒空白，既不是"没有新帧"，也不是采集脱节：帧线程被一轮模板匹配占住了 23 秒。**
（所以 §5 ④ 的静止兜底修不动它 —— 兜底轮排在那一轮后面，根本轮不到。）

### 9.1 铁证（真机 04:35，画面＝好友列表、跑号第 9 步；相邻两条统计行）

```
04:35:19.062  帧管线统计: 窗口 29087ms 接收 164 帧 / 处理 12 帧；识别 12 轮   （≈2.4 秒/轮）
04:35:42.315  MM-NameReader: 文字识别：区域 565x921 → 放大 ×3，读到 9 行
04:35:42.341  帧管线统计: 窗口 23294ms 接收 1 帧 / 处理 1 帧；识别 1 轮        ← 23.3 秒只跑了 1 轮
```

`窗口 23294ms / 接收 1 帧 / 处理 1 帧` ⇒ 这 23.3 秒里帧线程**只取到并处理了 1 帧**。

### 9.2 成因

产物里「列表区域」（`friend_list_area`）的**角色是 `ANCHOR`**，而 `AnchorLocator.locate(状态)`
会对该状态的**全部锚点**做模板匹配 ⇒ 这条 **431×511** 的大模板（窗口收紧后仍 565×921）跟着一起扫：

```
粗搜 ≈ 1.43 万网格点 × 约 11 万采样点 ≈ 1.6e9 次乘加
精搜 ≈ 576 位置 × 22 万像素      ≈ 1.3e8
⇒ 这条独占单轮匹配成本的 97% 以上（其余 14 条合计 ≤5e7）
```

同轮另一处可能拖时间的 OCR 有**代码级上界约 1 秒**
（`MlKitNameReader`：`Tasks.await(…, 1_000ms)` 到点即返回、同步跑在帧线程上），量级对不上。

### 9.3 修复

`PatrolAnchors.nonLocatableAnchors`（派生自 `nameAreaAnchors`）→
`CalibrationData.toAnchorLocator(nonLocatable = …)` → `CaptureService` 三处调用点传参。
**`windowRegions` 刻意不排除**：那块窗口正是文字识别的输入范围（不灰度化 OCR 会读到全零像素）。

### 9.4 证据与验证

- 证据：`docs/verification/m4/t4-perf-anchor-locate-scope.txt`
- 离线：`:app:test` 真全量 **641 例 / 0 失败**；新增 4 例单测钉住契约（区域锚点不进定位、窗口仍在）。
- **待做（需真机）**：走 §2 同一条路径（只拜访 → 第 9 步），确认
  `帧管线统计: 窗口 …` 维持 1 秒级、`friend_list_area` 不再出现在定位里。

### 9.5 教训（补 §8）

"识别没跑"这个现象，我（前任接手者）**连续两轮**都往"采集/帧"方向找答案，
而没先去问一句：**帧线程这一整轮到底在算什么？** —— 成本模型（位置数 × 采样数）
本该是排查这类"停摆"的**第一件事**，尤其当状态里存在比同类大两个数量级的模板时。
教训：**"没输出"先怀疑"还没轮到输出"，再怀疑"没东西可输出"。**
