# 架构（草案）

> 状态：草案。所有"开放决策"落地后，必须新增对应 ADR，并回来更新本文件。
> 本文件是实现手段的存放处（术语见 `glossary.md`）。

## 分层（概念层，不绑定具体技术）

| 层 | 职责 | 关键约束 |
| --- | --- | --- |
| 平台适配层 | 授权管理、前台判定、悬浮窗容器、后台服务生命周期 | 对外提供"是否前台 / 是否已授权"独立信号 |
| 采集层 | 获取屏幕画面 | 耗时受 §6 约束；不得改变识别结果 |
| 识别层 | 标志检测，产出判定记录（命中、位置、置信度、竞争位置） | **纯逻辑**：输入画面数据、输出判定；不依赖安卓框架，可在 JVM 离线回放；**搜索范围由外部注入的期望集合决定** |
| 决策层 | 状态机（滞回）、可信性判定、优先级仲裁（FR-01 > 巡查） | 唯一有权决定"是否动作"的层 |
| 执行层 | 点击转发（**坐标换算** + **输入拟人化抖动** + 间隔 ≥300ms）与点击审计 | 唯一有权下发点击的层；**常驻守护未启动** / 非前台 / 未知 / **换算后落点越界**时拒绝下发 |
| 流程层 | 巡查状态机（10 步）、中断 / 继续 / 跳过、记录与汇总 | 每步先验证后推进；失败即停。**每步两道闸**：① 重试 3 次（**看清了但不对**，含锚点没定位到）② **时间预算 15s**（从进入该步起算，"画面还没看清"只等不计次） |
| UI 层 | **导航壳**（`ui/nav/`：`Routes`（纯逻辑，可单测）+ `AppDestination`（图标与文案）+ `MasterMechanicApp`（抽屉 + `NavHost` + 底栏）；2026-10-01 M5-U1 起替掉 `MainActivity` 的 `when(screen)` 编号）、各页面（授权 / 运行 / 拜访设置 / 账号与好友 / 标定 + 抽屉四页）、悬浮窗内容与交互 | 悬浮窗可见性、位置、展开态不影响识别 |

## 不变量（任何设计都不得违反）

1. 识别结果与悬浮窗状态无关（§5-6）。
2. 非前台 → 不下发点击、不推进巡查、不消耗滞回计数（FR-09）。
3. 所有点击唯一出口在执行层，且每次点击必须携带判定记录 ID（NFR-05）。
4. 识别层不含任何与设备绑定的常量（§5-5）。
5. 识别层对画布几何透明：同一标定产物在竖 / 横画布会话下判定一致（输入先按画面区归一到标定几何，[ADR-007](decisions/ADR-007-画布方向适配.md)）。

## 识别范围：期望集合驱动（T2-1，2026-09-13）

| 项 | 约定 |
| --- | --- |
| 搜索范围 | 每轮只搜**外部注入的信号名集合**（`ExpectedSignals`）：**不外扩、不兜底**；集合内全不命中 = 「这一步没等到」（连续 3 轮 → 「未知」） |
| 空集合 | = 本轮不搜：不产生判定记录与耗时样本，对状态机如同不存在（不消耗滞回计数） |
| 窗口收紧 | **加载产物时按 `CalibrationStore.WINDOW_SHRINK_FACTOR = 0.6` 以中心收窄搜索窗口**（2026-09-21 提速）：成本 ≈ 可滑动位置数 × 模板采样数，收 0.6 → 位置数 ≈ 1/6；同时候选变少 → 误匹配概率更低。产物文件不动，回退改回 1.0（不必重标定）；离线锚点探针（真机 76 帧）验证 11 条命中率与分数不变 |
| **小模板最小余量** | 收紧时半宽**不低于「模板半宽 + `SearchWindow.MIN_ABSOLUTE_MARGIN_PX`(8px)」**（上限仍是原窗口）：小选区窗口本来就小（= 选区 ×3），再乘 0.6 就快贴着模板——`launch_switch`（9×15 模板 / 27×45 窗口）收紧后只剩 16×27，启动页渲染未稳时连 miss 两次。加下限后 25×31（位置数 104→289，仍是最便宜的一类）；大窗口（141×36 → 232×61 半宽 ≫ 下限）**逐值不变** |
| 未标定名 | 期望里出现产物中不存在的信号名 → 剔除，不记入本轮搜索量 |
| 守护待命 | **两部分并集**（2026-09-20 起）：① **遮挡屏**标志（`PopupWatchExpectedSignals`，恒定搜、不参与阶段推进 —— 2026-09-19 删掉"命中启动页/大厅就开关窗口"的推断，因为大厅可能一闪即被弹窗盖住；**2026-09-29 起 = `UiState.guardedOverlays` 三屏**：活动弹窗 + 新手引导 + 新手大厅）；② **能当起点的 5 屏**（启动页 / 服务器列表 / 大厅 / 自己农场 / 好友农场，`PatrolScenes.startStates` → `PatrolDrivenExpectedSignals.standbyStates`）。**②必须有**：菜单的起点判定要先知道"用户在哪一屏"，少了它状态恒「未知」→ 点菜单永远不启动（2026-09-20 真机死锁）。**成本账**：+5 条 ≈ +350~500ms/轮，但状态能收敛 → 节流从"永不降档的 200ms"落到 1000ms → 单核占用 ≈29% → 33%（净 +4pp）。⚠ 新手两页的标志**未标定时被剔除**（不记入搜索量），标了才生效。 |
| 守护待命的备选（评估过未采用） | ① **点菜单后才注入起点场景**：待命期零成本，但状态判定要连续 2 轮（§2.2 滞回）→ 首次点击有 0.4~2s 延迟、判定要从"同步读状态"改成"挂待启动 + 轮内判定 + 超时"的异步件，且待命期状态仍恒「未知」→ 降档依旧失效（除非另改 `settled` 判据）；② **菜单展开时才注入**（点手柄 → 开始搜 → 收起即停）：待命期零成本、点击时通常已收敛（读菜单 1~3s ≫ 2 轮），代价是多一条"菜单开合 → 期望集合 / 节流档"的接线，极端情况（展开后 <0.4s 就点）要兜底提示再点一次。**当前采用 ②之外的最简做法**（待命期直接搜），因为它是唯一"零延迟、同步判定、无新时序"的一版 |
| 演练 / 离线回归 | 显式声明全集（`ExpectedSignals.ALL`，等价改动前的「全扫轮」）：M1 判定路径与固定批次回归走这条 |
| 已取消 | 按状态自动选子集、状态未知即全扫、按需补扫、周期兜底 |
| 可审计性 | `RoundResult.searched`（非空集合，空 = 不搜）+ 运行日志「本轮搜索集合变化」：真机可直接读出阶段推进与每轮实际搜索范围 |

阶段推进用**本轮原始命中**而非滞回结论：等 2 轮确认才注入，会让刚弹出的弹窗在本轮与下一轮都搜不到。

## 点击坐标：帧几何 → 屏幕几何（2026-09-20 真机缺陷驱动）

| 项 | 约定 |
| --- | --- |
| 为什么要有 | **识别读的是帧、点击打的是屏幕**，两套几何只在"帧 == 屏幕"的会话（横画布）恰好相等；竖画布会话（帧 1440×3168 / 屏 3168×1440）下原样下发会落到屏幕外——真机实录"点了毫无反应" |
| 公式 | `屏幕 =（帧坐标 − 画面区左上）× 屏幕尺寸 / 画面区尺寸`；画面区取自识别层同一几何（`CanvasGeometry.contentArea`），**不另写一套** |
| 实现点 | `ClickForwarder`（**唯一下发口**，第 5 条职责）。请求仍只带帧坐标（坐标必须来自识别判定结果）；换算后交给 `dispatchGesture` 的是屏幕坐标 |
| 三方几何 | 标定帧尺寸（产物）/ 运行帧尺寸（采集）/ 屏幕尺寸（运行时读，红线 4）——任一缺失 → **不换算**（原样下发），**绝不猜** |
| 越界即拒 | 换算后落点不在显示区域内 → 拒绝下发（`OUT_OF_SCREEN`）；门禁顺序：守护 → 非前台 → 未知 → **越界** → 串行 → 间隔（原「演练」一拦随点击模式一并移除，2026-09-22） |
| 审计 | `MM-Click` **同时记帧点与屏幕点**：真机"点歪了"必须能分清识别定位错与换算错 |
| 谁负责刷新 | `CaptureService` 每帧重算并按**变化**推送（转屏 / 重开会话自愈）；会话结束清回 `IDENTITY` |

## 运行门槛：常驻守护是**必备项**（2026-09-20 用户口径）

| 项 | 约定 |
| --- | --- |
| 为什么 | 菜单请求由常驻守护服务接收（`PatrolRequestConsumer`）。它没起时，此前表现为"菜单请求发出去了、流程不启动"——**看着在跑、其实没人接单**（真机上连踩两次） |
| 界面 | `AuthItem.RESIDENT`：与其它授权同级的卡片，未启动 → 红字「未启动」+ 按钮「启动守护」+ 描述写明"不启动时整个自动化都不动作"；授权汇总「全部就绪」把它算进去。**标签上不标"（必需）"**（2026-09-20 用户口径） |
| 授权页顺序 | **无障碍 → 常驻守护 → 通知 → 屏幕采集**（`AUTHORIZATION_DISPLAY_ORDER`，有单测钉住）：屏幕采集**必须最后**——点它会跳到《王者荣耀》，其余三项排它上面才不会让用户来回跳两趟 |
| 门禁 | `ClickDispatch.guardRunning`（默认 **false**，`ResidentService.onCreate/onDestroy` 置位）→ `ClickGate` 拒绝原因 `GUARD_NOT_RUNNING`，排在门禁**首位**（2026-09-22 起「演练模式」一拦已删除）⇒ **守护没起 = 流程点击与 FR-01 自动关弹窗一律不下发**（审计留痕） |
| 菜单 | `FloatingWindow.startBlockReason` 最先检查消费方是否就位 → **所有动作**（拜访 / 换号 / 继续 / 停止）都保持展开并挂原因条 |
| 反向约束 | 守护停止（服务被回收 / 用户停止）→ `PatrolRequestConsumer.uninstall` + `PatrolSession.stop` + 门禁随即拒绝 ⇒ "停守护 = 自动化整体停"，不会留下半死状态 |

## 节流两档的取值（NFR-02：上界，不是固定值）

| 档 | 值 | 依据 |
| --- | --- | --- |
| 快档 | 200ms | 需求「需要响应时 ≤0.2s」；与人工"看到界面 → 点击"的 200~400ms 同量级 |
| 稳定档 | **500ms**（2026-09-20 由 1000ms 调小） | 需求「确实稳定时 ≤1s」是**上界**；用户口径"App 不会一直挂后台、跑完就退出，不必省资源"。一次状态推进 = 2 个轮次（§2.2 滞回），故每降 500ms 就快 ~1s |
| 额外规则 | **动作即回快档** | 点击下发（跑号 / FR-01）与流程相位变化（启动 / 继续 / 步骤推进 / 停止）立即切快档——降档只看"上一轮是否稳定"，不知道"我们自己刚推动了画面"，否则白等一整轮（实测 1.44s / 1.84s） |
| 回退 | 把 `STABLE_INTERVAL_MS` 调回 1000ms | 唯一改动点；将来要长时间挂机时用 |
| **去掉稳定档？**（2026-09-21 用户提议"改暴力搜索"，**评估后不采用**） | **不采用** | 收益比想象小：点击路径本来就"动作即回快档"，去掉稳定档只影响"不点击的等待段"，每步约省 0.2~0.4s。代价：单核占用 **20% → 38%**（≈2 倍，按单轮 0.12s / 固定 200ms 算），且**违反 NFR-02 验收要点**「稳定挂机时资源占用**显著低于**固定短间隔轮询」——固定 200ms 就是固定短间隔轮询。同一轮真正的大头在「点击后的观察窗口」，见下节 |

## 点击后的观察窗口：上限 2s + 提前结束（2026-09-21 用户"流程慢"驱动）

| 项 | 约定 |
| --- | --- |
| 原来错在哪 | `SETTLE_WAIT_MS = 2000` 是**一律等满**。真机时间线：点完 0.96s 就已确认画面换了，却硬等到 2.1s 才点下一枪 → **每步白等 ≈1.0~1.4s**（≈80% 的步耗时），一串 7 步白等 8~10s |
| 判据（三条全中才提前） | ① 记下了"点击那一刻的画面"；② 当前画面不是 `未知`；③ 当前画面**不是点击时那一屏**，**且这一步在新画面上确实有事可做**（`PatrolAnchors.actionFor` 非空） |
| 为什么带第 ③ 条 | 只要求"画面变了"的话，点歪之后画面切到别处也会立刻放行 → 失败被**提前**记进重试。带上它 ⇒ **快只快在成功那条路上，失败路径的耐心与计时一点没减** |
| 记录点 | `PatrolFlow.acted(state, nowMs, clickedState)` 把画面写进 `State.stateAtLastAction`；为 null（纯逻辑 / 离线重跑）→ 退化为老行为 |
| 日志 | `流程: 第 N 步：点「X」，之后应看到「Y」（画面已切换，观察窗口提前结束）`——提速必须**在日志里看得见** |
| 预期 | 点击→点击 ≈2.1~2.6s → **≈0.6~1.0s**；`刚点过，等画面切换` 应只在画面确实没变时出现 |
| 证据 | `docs/verification/m4/t4-settle-window-and-tiny-margin.md` |

## 标定产物的记录：元素 / 角色 / 用途 / 备注（2026-09-19 用户口径）

一条记录 = **元素 ID** + 角色（标志 / 锚点）+ 搜索窗口 + 模板（可多样式）+ **用途**（仅锚点）+ **备注**（自由文本）。
**同一个元素的两条记录共用同一个 ID** —— 清单把「标志 + 锚点」认成一行的依据就是"ID 相等"。

| 字段 | 谁在用 | 口径 |
| --- | --- | --- |
| 元素 ID | 程序 | 由「落到哪个元素」决定（`CalibrationSignals.targetFor`）：**锚点 = 用途名**（`hall_farm`），**其余 = `<界面>_e[n]`**（`activity_popup_e1`）。它**不是**像素哈希——见下 |
| 角色 | 判决 | 标志进状态判定；锚点只回答"点哪里"（§2.1）。同一 ID 可以两条（每个角色一条），唯一性判据是 **(ID, 角色)** |
| 用途 | 流程 | 锚点的契约名（`hall_farm`），标定页从 `PatrolAnchors.purposesFor(state)` 选；查找走「状态 + 用途」（`anchorIdFor`） |
| 备注 | 人 | **可空、可重复**，不参与识别与流程；元素级（同 ID 的两条共用一份，重标时没填就沿用旧的）；详情弹窗里改（输入框在图片下方） |

**为什么"元素 ID"不是图片 MD5**（一次被实测否掉的方案，2026-09-19 用户反馈）：

> 最初用「模板像素的 MD5 前 8 位」当 ID，图的是"同一张图 → 同一个 ID → 重标即覆盖"。
> 用户实测指出：**人不可能每次都框出一样的像素**——差一个像素 MD5 就变，"覆盖"形同虚设。

所以身份改由**语义**决定，像素只决定"长什么样"：

| 写入情形 | 落到哪 | 效果 |
| --- | --- | --- |
| 勾了**锚点**且选了用途 | 该用途那个元素（`hall_farm`） | **同一个用途再标一次 = 覆盖**（不必框得一样） |
| 其余（只写标志 / 锚点没有用途，如**活动弹窗**） | 下一个空的 `<界面>_e[n]` | **新增一条** |

只有这两条，没有"让用户挑"的第三档：2026-09-19 晚用户拍板**移除「写入到」那一行**——
一个有用途的锚点本来就该只有一条记录（不会像你说的"多次新增相同的锚点用途、命名都相同、无法区分"），
再让人从一列元素里挑"这次覆盖谁"既多余又容易选错；而**活动弹窗**确实有多个相似模板，
它每次框选都是新增一条（名字 `_e2` / `_e3` 天然可区分）。
槽位后缀刻意叫 `_e`（元素）而不是 `_marker`：一条槽位**可能同时是标志和锚点**（活动弹窗就是这样），
名字里带 "marker" 会让人以为它只是标志。

**删除** = 清单行**左滑 → 行尾压出红色删除按钮 → 点按钮**，与服务器清单 / 好友清单同一套
（`ui/list/SwipeActionRow` + `ServerListGestures`），**删除即生效 + Snackbar 撤销窗口**（不弹二次确认）。

配套的三件事：
1. **不用给东西取名**：用户只写备注（可选），名字由程序按上面的规则算；
2. **产物只读 v3**：v1/v2 不再兼容（用户口径：旧产物全部删掉重标），报错里直接写"请删除产物后重新标注"；
3. **日志自带产物清单**：会话建立时逐条打 `元素ID ｜ 角色 ｜ 界面 ｜ 用途 ｜ 备注 ｜ 模板 ｜ 窗口`，
   之后任何一行点击日志（`锚点: hall_farm`）都能直接读懂，不必回标定页翻。

### 破坏性操作：确认与恢复（2026-09-20 用户口径）

依据是**代价不对等**：删一行重框一次就回来了 → 只要撤销；而清空帧池要**回游戏重跑一遍各界面**、
删除产物要**重框 11 条锚点 + 10 个界面标志** → 这两件事**先问一次，再给恢复**。

| 操作 | 确认 | 恢复 |
| --- | --- | --- |
| 删一行（清单元素 / 服务器 / 好友） | 不弹（左滑已经是一次明确的动作） | Snackbar「撤销」 |
| **整体清空清单**（服务器 / 好友） | **二次确认弹窗** | Snackbar「撤销」（**清空前的整份清单**写回 —— 顺序、内容原样还回来） |
| **清空帧池** | **二次确认弹窗** | Snackbar「撤销」＋**卡片上常驻的「恢复上次清空的 N 帧」** |
| **删除整个产物** | **二次确认弹窗** | Snackbar「撤销」（快照写回） |

四处的**恢复都是"整份快照写回"**，只是快照的粒度不同：一行要插回**原位**（得存位置 + 内容），
而"清空 / 整份删除"存的就是清空前的**那一整份**（产物 / 服务器清单 / 好友清单都是 KB 级文件，
整份写回最简单也最不会错）。

- **帧池的"清空"其实是软删除**：帧被移进 `files/calibration/frames-trash/`（`CalibrationFramePool.clear`），
  「恢复」就是从回收站移回。**回收站只保留一代**——下次清空前把上一代真删：
  磁盘占用有上界（最多两代），而"刚清错的那一次"一定救得回来。要更长的历史就得引入体积与清理策略，不值得。
- 恢复入口给两个，是因为**Snackbar 只活几秒**，而"清错了 49 帧"这件事可能过一会儿才发现。
- 产物那两条共用同一个撤销快照 `PendingUndo(message, before)`：要恢复的东西本来就是**同一份整份产物**
  （`CalibrationData`，体积很小），不必为"按位置插回"再写一套逻辑。

## 清单改名 / 删除：跨文件引用（好友 / 区服，2026-09-22 用户口径）

名称（好友名 / 区服名）是**跨文件的引用键**，清单只是它的**主副本**，别处存的是副本：

| 主副本 | 下游引用 | 只在…时有值 |
| --- | --- | --- |
| 好友清单 | ① `preset/visit.txt` 的"拜访谁" ② 标定产物里带**归属好友名**的锚点（v4 第六段；2026-09-23 起界面不再产生这种记录，只读旧产物） | ② 只在旧产物里还有那种记录时有 |
| 服务器清单 | `preset/visit.txt` 的 `serverName` | 只在策略＝**固定区服**时有（顺序轮换时它本来就是空串） |

只改清单 → 下游指向一个**不存在的人 / 区服**。而两处文件单看都合法 ⇒ 症状只在运行时表现为"莫名中止"，
事后极难归因：好友侧是"第 9 步在列表里找不到行"（红线 3 不挑"最像的"）；
区服侧是"换号那一步永远找不到区服"（区服名是唯一参与定位的字段）。

### 改名：把引用**改挂过去**（`friends/FriendRenameSync` / `servers/ServerRenameSync`）

| 项 | 约定 |
| --- | --- |
| 入口 | 清单**编辑保存**（`FriendListScreen.renameAt` / `ServerListScreen.renameAt`）；**新增**不走同步 |
| 顺序 | **先落盘清单、成功了再同步**（清单是主副本）；同步失败**不撤销**改名 —— 改名本身已成功，撤销只会让人以为没改上、再改一次还是同样的失败 |
| 匹配 | **全等**（`VisitPreset.renamedFriend` / `renamedServer`、`CalibrationData.renamedFriend`），与红线 3 同源 |
| 只改名字 | 好友侧：模板 / 窗口 / 用途 / 角色 / 归属规则一概不动（改名 = 同一个人换了名字，划过的框仍然有效，否则等于逼用户重标一次）；区服侧：**策略与好友一格不动** |
| 失败 | 不吞：`Report.failure` 带原始原因 → 界面提示"已改名，但…没跟着改：<原因>" |
| 提示 | 按"下游跟着改了没有"分档（好友 4 档 + 失败 / 区服 1 档 + 失败）—— 因为这决定用户"还要不要去别处手工改" |

产物写回仍走 `CalibrationStore.save`（临时文件 + rename），因此自动带上"写完通知采集侧就地重载"
（`CalibrationReloadSignal`），改名后不必停开采集。

### 删除：先**验证引用**、有引用就**先问一句**（`friends/FriendReferences` / `servers/ServerReferences`）

删除没有"新的名字"可改挂 —— 引用只会变成**悬空引用**。程序**不替用户清理引用**（那是悄悄改数据，
而且"删了这条就顺手清掉预设"很可能是用户没要的），所以删除这一侧只做一件事：**说清楚**
（`friendDeleteConfirmBodyOf` / `serverDeleteConfirmBodyOf` 管**动手前**问的那一句，
`friendDeleteNoticeOf` / `serverDeleteNoticeOf` 管**删完之后**撤销窗口里说的那一句）。

| 项 | 约定 |
| --- | --- |
| 时机 | **删前查**：查到"有引用"或"没能确认" → **先弹确认框问一句**（正文讲"删了之后会怎样"）；查到"没引用" → 不打断，照旧"先做再给撤销"（左滑 + 点按钮已是两步明确意图） |
| 删后 | 撤销窗口那一句仍带同一份结论（用户点「仍要删除」才真删，`hits` 随 `*DeleteAsk` 一直存到删完），使"动手前问的"与"删完说的"不会各说一套 |
| 撤销窗口时长 | **`SnackbarDuration.Long`（约 10s）**，不是 `Short`：删除不可逆、**这里是唯一的挽回入口**（2026-09-22 用户口径"撤销按钮驻留太短"）；标定页帧池「清空」也同一档 |
| 只读 | 查询**不动任何文件**；结论只影响文案与"问不问" |
| 匹配 | **全等**，与改名 / 红线 3 同源 |
| 失败 | 读盘失败 → 报"**没能确认**下游引用（原因）"，**绝不**退化成"没引用" —— 把"查不到"说成"没问题"是最坏的一种撒谎；且**照样先问一句**（结论不可信时按"有风险"处理） |
| 提示分档 | 好友：没引用 / 拜访规则在用 / N 条标定记录在用 / 两处都在用 + "没能确认"；区服：没引用 / 拜访规则固定用着 + "没能确认" |
| 清空 | 清空**本来就有**确认框 ⇒ 引用信息就放在**动手前**的正文里（"其中 N 条还被引用"；三态 `Checking` 先按普通句 / `Done` 说条数 / `Failed` 如实加一句），撤销窗口只说"清了多少条"，不重复 |

## 流程主流程（换号 / 拜访）：识别 ↔ 步骤的接线（M4-T4-2 / T4-3）

流程层被拆成两个文件，边界刻意画在"认不认识识别"上：

| 文件 | 认识什么 | 不认识什么 | 为什么这样切 |
| --- | --- | --- | --- |
| `patrol/PatrolFlow.kt` | 步骤编号、区间（只换号 / 只拜访 / 换号 + 拜访）、起点判定、单步重试上限、`resume` | `UiState`、识别、坐标、点击 | 它是 FR-04 那张表本身；单测不需要任何识别概念 |
| `patrol/PatrolScenes.kt` | `UiState` ↔ 场景、每步的验证目标、每步的**动作所在状态** | 坐标、点击 | "哪块画面 = 哪个场景"只在这里接一次线 |
| `patrol/PatrolAnchors.kt` | 每步在哪个状态点哪个**锚点名** | 坐标、点击 | 名字是标定与流程之间的**契约**，两边必须同一份事实 |
| `patrol/NameLocator.kt` | 按名字在一屏候选里挑**唯一**那个 | 坐标、点击 | 第 5 / 9 步不走锚点：挑哪个不是位置问题，是内容问题 |

四条接口口径：

1. **「弹窗遮挡」与「认不出来」必须分开**（`PatrolScenes.Reading`）：前者等 FR-01 关掉弹窗就恢复，
   后者要叫用户来看；合成一种就会因为一个弹窗白白中止整条流程。
2. **每步两个状态**：`actionStates`（动手前必须先确认的画面，锚点只在这里找）与
   `expectedState`（做完之后应该看到的画面）。两者**不得重叠**——重叠意味着"点完立刻自证通过"，验证会退化成空转。
3. **一步可以点好几下**（`PatrolAnchors.Action` 的链）：如"退出农场"= 农场返回 → 返回场景确认框选「返回大厅」；
   "退出登录"= 大厅设置入口 → 设置页退出登录 → 确认框确认。**每一击都带自己的验证目标**（`expect`），
   链的最后一击的 expect 必须等于 `PatrolScenes.expectedState`（由单测钉住）——否则就是"点完不验证"（红线 5）。
4. **用途是契约、名字不是**（2026-09-19 用户口径）：标定产物的锚点元素 ID **就是用途名**（`hall_farm`），
   用户不必关心"这条叫什么"，流程要找的也正是 `purpose` 这个字段（11 条，见 `PatrolAnchors.all`）。
   同一个界面有两个控件时（大厅 = 设置入口 + 农场入口）→ 标定页让用户选**用途**（T4-3a）；
   单控件界面（活动弹窗）`purpose` 为空——FR-01 按状态取锚点，不看用途。
   查找一律走「状态 + 用途」（`CalibrationData.anchorIdFor`），**找不到就说"这个用途还没标定"**，绝不拿别的锚点去点。
5. **不兜底**：`actionFor(step, state)` 在状态不匹配时返回 null，而不是换个状态再找一遍；
   拿别处的锚点去点，落空是安全的，猜中才是危险的（红线 3）。
6. **名称定位两档 + 重试绑在"新的识别结果"上**（2026-09-22 真机驱动）：`NameLocator.locateContaining`
   （好友名）先走**严格档**（去空白后包含），一屏一个都不中时才走**宽松档**（目标与候选都只留
   字母 / 数字 / 汉字再比包含）。**唯一性两档一样严**：0 个或 ≥2 个都停下（红线 3 未放宽，放宽的只是
   "算不算命中"）。依据是真机日志：用户配的名字与游戏内**完全一致**（`Boss~~喵`），OCR 却把 `-` 插到了
   名字**内部**（`立Boss-~~喵(阿娜雅)`）⇒ 只去空白不够，符号也不能当真。两处例外：`locate`（区服全等，
   FR-10）不放宽；目标"只认字"之后会空掉的（纯符号）不放宽 —— 否则每一行都会命中。
   配套：**重试必须花在新的识别结果上**。OCR 有 `OCR_MIN_INTERVAL_MS = 1000` 复用，而帧轮 200 / 500ms
   ⇒ 若"每轮记一次失败"，`MAX_RETRIES = 3` 会在 1 秒内烧完、实际只对应 1 个新结论（**等于没有重试**）。
   `visitPlanOf` 因此对**复用的结果**只回 `Waiting`、不判 `Failed`（行内图标没定位到仍按当帧判 —— 那是
   每帧新算的）⇒ 3 次重试 ≈ "≥3 个新识别结果都找不到"，墙钟 ≥3 秒，仍由 `STEP_TIMEOUT_MS = 15s` 兜底。

> 「好友列表 / 设置页 / 退出登录确认框 / 返回场景确认框」认得出来但**不是 FR-04 的合法起点**（起点表里没有它们）
> → `PatrolFlow.firstStep` 对 `Scene.NOT_A_START` 返回 null、由调用方提示用户先退出来。
> 保留这个场景值就是为了让"认得出但不是起点"与"认不出画面"可分。
