# T4 提速第二轮：观察窗口提前结束 + 小模板最小余量（2026-09-21）

用户口径：① 按上轮建议做小模板余量硬化；② "整个流程还是有点慢，能否去除 500ms 限制、改为暴力搜索"。
本文件记录 ① 的实现与证据、② 的成本核算（**经核算未采用**，理由见第三节）。

----------------------------------------------------------------
## 一、时间到底花在哪（真机 2026-09-21 00:23 会话，逐步拆开）

| 环节 | 每步耗时 | 说明 |
| --- | --- | --- |
| **点击后的观察窗口（固定 2s）** | **2.0s** | `PatrolRunner.SETTLE_WAIT_MS`：点完一律等满，期间不点第二下 |
| 画面切换 → 确认（滞回 2 轮） | 0.5~1.0s | 含游戏自身 0.3~0.5s + 2 ×（单轮 0.12s + 间隔 0.2s） |
| 锚点定位 | 1 轮 ≈0.32s | 与上一条重叠 |
| 节流间隔本身 | 快档 0.2s × 2 轮 = 0.4s | **"动作即回快档"已生效**（点击路径本来就在快档） |

真机实录（同一串动作）：

```
00:23:29.156  点 hall_settings
00:23:30.112  大厅 -> 设置页（连续 2 次命中）      ← 0.96s 就知道画面换了
00:23:31.273  点 settings_logout                  ← 却又等了 1.16s 才动手
```

结论：**每步 ≈80% 的时间花在"已经知道画面换了、却还要等满 2s"上**（≈1.0~1.4s/步），
而不是花在节流间隔（0.4s）或识别（0.12s/轮）上。

----------------------------------------------------------------
## 二、做法：观察窗口从"固定 2s"改成"上限 2s + 提前结束"

判据（[PatrolRunner.screenMovedOn]）三条同时成立才提前结束：

1. 记下了"点击那一刻的画面"（没记 → 退化为老行为）；
2. 当前画面**不是 `未知`**（加载中交给"画面还没看清"的耐心逻辑）；
3. 当前画面**不是点击时那一屏**，**且这一步在新画面上确实有事可做**（`PatrolAnchors.actionFor` 非空）。

第 3 条里的"有事可做"是关键：只要求"画面变了"的话，点歪之后画面切到别处也会立刻放行，
失败会被**提前**记进重试。带上它之后——**快只快在成功那条路上，失败路径的耐心一点没减**。

真机日志新增可见标记（验收时直接看这条）：

```
跑号: 第 4 步：点「launch_switch」，之后应看到「服务器列表」（画面已切换，观察窗口提前结束）
```

预期效果：每步省 ≈1.4~1.9s；「换号 + 拜访」一串 7 步约省 8~10s（10s 级 → 3~4s 级）。

单测（`PatrolRunnerTest` 新增 5 例）：
- 画面换成"这一步能动手的地方" → 允许点，且 note 带"提前结束"；
- 画面没变 → 照旧等满（防连点）；
- 画面换成"这一刻不能动手"的地方（启动页） → **不提前放行**（失败耐心不变）；
- 画面变 `未知` → 照旧等（交给加载耐心逻辑）；
- 没记下点击时的画面 → 退化为老行为（纯逻辑 / 离线重跑不受影响）。

## 三、"去除 500ms、改暴力搜索"的成本核算（**未采用**）

| 方案 | 每步能省多少 | 单核占用 | 需求验收 |
| --- | --- | --- | --- |
| **去掉稳定档**（一直按快档 200ms 跑） | **≈0.2~0.4s**（只作用于"不点击的等待段"；**点击路径本来就已回快档**，所以这条几乎白花） | **20% → 38%**（≈2 倍） | **违反** NFR-02 验收要点「稳定挂机时资源占用**显著低于**固定短间隔轮询」——固定 200ms 就是固定短间隔轮询 |
| **观察窗口提前结束**（本次采用） | **≈1.4~1.9s** | 20% → 20%（**不变**） | 不涉及 |
| （若"暴力"指"每轮搜全部信号"） | 不省，**更慢** | 单轮 0.12s → 全扫 0.8s 级 | 期望集合机制本就只搜"当前该看的"，全扫没有收益 |

占用算法：单轮 0.12s（收紧后真机均值）。固定 200ms → 0.12/(0.12+0.2) = 38%；
快档 200ms + 稳定档 500ms → 稳定期 0.12/(0.12+0.5) = 20%。

结论：**用户想要的是"更快"，而"去掉稳定档"买到的是 2 倍 CPU 换 0.2~0.4s**；
观察窗口这一刀买到的是 **约 1.4s、零额外 CPU**。所以先只切后者——同一轮只动一个变量，才有干净的对照。

## 四、小模板最小余量（本轮第二件事）

问题（上轮真机观察）：`launch_switch` 模板 **9×15 px**、标定窗口 **27×45 px**（产物实测
`signal=launch_switch|anchor|0.620139,0.528093,0.638889,0.542298` @1440×3168 → 27×45）。
收紧 ×0.6 后只剩 **≈16×27 px**（可滑动位置 104 个），启动页刚出现、按钮还没渲染稳时连 miss 两次
（第三次才命中；离线探针显示收紧前后都是 7/7，**不是收紧引入的**，只是余量薄被暴露）。

做法（`SearchWindow.MIN_ABSOLUTE_MARGIN_PX = 8.0`）：收紧时半宽**不低于「模板半宽 + 8px」**，
且上限仍是原窗口（只收紧、不放大）。大窗口不受影响：

| 信号 | 模板 | 原窗口 | ×0.6 | 加余量下限后 | 受影响？ |
| --- | --- | --- | --- | --- | --- |
| `launch_switch` | 9×15 | 27×45 | 16×27 | **25×31** | **是**（位置数 104 → 289） |
| `launch_login` | 129×34 | 387×102 | 232×61 | 232×61 | 否（≈127/32 px 半宽 ≫ 下限 72.5/25） |

代价可忽略：`launch_switch` 的位置数 ×2.8，但它本来就是最便宜的一类（位置数 × 采样数，量级 ~10⁴），
相对大窗口（`server_select_e1` 等 10⁶ 级）可以忽略。

### 证据（离线锚点探针，与生产同源：同一系数 + 同一收紧函数）

## 五、真机验收要点（下一轮演示时看这几条）

1. **提速**：日志里点击→点击的间隔应从 ≈2.1~2.6s 降到 **≈0.6~1.0s**；
2. **可见标记**：出现 `（画面已切换，观察窗口提前结束）`；
3. **没有连点**：`刚点过，等画面切换` 应当**只在画面确实没变**时出现；
4. **大窗口耗时不变**：`信号耗时统计` 里 `server_select_e1` 等仍 ≈32ms（余量只影响小模板）；
5. 演示路径仍应走到 **第 5 步按预期停下**（名称定位未落地，T4-3）。
