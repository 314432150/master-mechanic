## 3. "切换慢"的根因（用户反馈，本次量化）

实测延迟：**未知→启动页 ≈6.2s**（06:38:49.06 首轮 → 06:38:55.29 确认）；
**启动页→选择服务器 ≈3.2s**（06:40:17.5 前一命中轮 → 06:40:20.73 确认）；
**选择服务器→启动页 ≈3.4s**（06:40:36.4 → 06:40:39.80 确认）。

机制（两轮 + 稳定档间隔）：

1. **轮 A**：画面已切换 → 当前状态 `未命中` → 触发**补扫**（T1-10g）发现新状态命中（`candidateStreak = 1`）
   但**该轮没有发生转移** → `RoundResult.stable = (transition == null) = true`
   → **仍按稳定档 3000ms** 排下一轮（节流未降档）；
2. **轮 B**（+3s）：`candidateStreak = 2` → 转移 → 此时才降档 1000ms 并输出状态变化。

→ **总延迟 = 0~3s（等轮 A）+ 3s（等轮 B）= 3~6s**。

根因：**「已有候选累积（疑似转移）」没有被当作"变化中"**，节流仍按稳定档等待确认轮。
（NFR-02 本意是"变化中 0.5~1s、稳定 3~5s"；候选已出现即属"变化中"，当前实现偏保守。）

### 建议优化（不改需求参数，单点改动）

- 让 `stable`（降档判据）改为 **"本轮无转移 且 无候选累积"**（`candidateStreak == 0` 且当前状态未命中计数为 0）；
- 效果：轮 A 一旦出现候选即降档 1000ms → 轮 B 间隔 3s → 1s → **总延迟 1~4s（平均省 ~2s）**；
- 稳定档保持 3000ms 不变（仍满足 NFR-02 的 3~5s），仅在"疑似转移"时用变化档。

实现落点（**T1-13 已实施**）：`UiStateMachine.hasForeignCandidate` + `RecognitionLoop.RoundResult.settled`
（预期命中 ∧ 无候选累积 ∧ 无转移）；`CaptureService` 以 `settled` 选择节流档，两档数值同时由 T1-13 调整为
**200ms / 1000ms**（间隔语义改为「两轮之间的休息时间」，新增 `FrameThrottle.markProcessedEnd`）——
即本文上一节观测到的 "0~3s / 3~6s" 系改造前数据。
