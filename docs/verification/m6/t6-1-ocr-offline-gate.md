## 3. 关键证据

### 3.1 `999`（唯一硬指标）：三种读法都读对

设备原图 `mm-shot.png`（3168×1440，2026-10-23 03:18 抓，立牌分享码弹框，真值 `999` / `UZQ5PN`）。

| 读法 | 输出 | 分数 | 耗时（桌面） |
| --- | --- | --- | --- |
| **rec-only**，产物窗口 `(1087,912)-(1183,962)` = 96×50（不跑检测，直接喂识别） | **`999`** | **1.0000** | **20ms**（22/20/20） |
| **det + rec**，放大到 280×140 的块 | **`999`** + `蒙顶级立牌` | 1.0000 / 0.9986 | 79ms |
| **det + rec**，整帧 3168×1440（40 个框） | **`999`** @框 `[1090,917,1179,962]` | **1.0000** | 2264ms |

### 3.5 交付用模型的复验（ONNX + onnxruntime，2026-10-23）

Paddle 的 `.pdmodel` 不能直接进安卓，所以先导出/取得 ONNX，**用同一批真机原图复验，再谈接代码**：

| 项 | 结果 |
| --- | --- |
| 模型来源 | `huggingface.co/SWHL/RapidOCR` 的 `PP-OCRv4/ch_PP-OCRv4_rec_infer.onnx`（PP-OCRv4 mobile rec 的 ONNX 导出） |
| 体积 | **10.35MB**（fp32；int8 量化失败，见下） |
| 用例 | `999`（mm-shot）+ 用户补的 7 张分数 = **8/8 全读对**，单块中位 **4ms**（桌面 ORT CPU） |
| 关键前提 | rec **只吃"一个数字块"**：把「数字 + 立牌名」整条喂进去会读成 `7号` / 空 ⇒ 先用 det 只做"找数字框"取景（离线工具），再喂 rec |
| 顺带发现 | 8 张弹框的分数框位置几乎重合（x 1085~1184，y 909~968）⇒ **固定窗口可用**，分数块不需要 det |

## 4. 换引擎后才暴露、判定层必须处理的两件事

### 4.1 低频字会认错（`蒙讶` → `蒙狂`，0.878）

同一帧里 `蒙狂顶级立牌` 的置信度 0.878（其余常规文字都在 0.99+）。ML Kit 这一格读对。
⇒ 红线 3 是**全等匹配**：认错一个字 = 名字对不上 = 流程停下。换引擎前要用真机名单统计一次
「名字级的逐字正确率」，否则会把"识别抖动"变成"流程中止"。

### 4.2 一行会被切成两块 / 等级数字被并进名字

旧池帧（竖屏带年代）：`67iu不错哦V（徐诏衍）` → `67` + `iu不错哦V（徐诏衍）`；rec-only 下 `77Boss~~喵（阿娜雅）` 丢前缀 `77`。
生产尺度帧（3168×1440，`1792700025004.png`）：`Boss~~喵（阿娜雅）` 被读成 **`80BoSS~~喵（阿娜雅）`** ——
**等级数字 `80` 直接被并进了名字**；同一帧 `细细の听(许畅)` → **`细细听（许杨）`**（`の` 丢、`畅`→`杨`）。
ML Kit 这两种都给的是干净的一行。

⇒ `NameCandidate` 的"一行"语义变了，`NameLocator` 的全等比较会失败；需要**同 y 带拼接 + 前后缀剥离**策略，
且这条策略必须先在一张真正的 25 行原图上量过再定（否则等于盲改判定层，违反 §2「不动判定层」）。

**但同一条行带、跳过 det 直接 rec，问题就没了**（2026-10-23 实测，同一帧第 2 行）：
裁 `(2100,415)-(2500,495)`（只含名字、不含等级角标）→ rec-only 得到 **`Boss~~喵（阿娜雅)`**（0.9063，**20ms**），
不再有 `80` 前缀。⇒ 既然判定层本来就有「行带」，**接入时应按行带切给 rec、完全不跑 det**：
25 行 × ~20ms ≈ 500ms（桌面），并且天然没有"断行/并名"。
⚠ 唯一残留：括号全半角不统一（读到 `（阿娜雅)`），而 `NameLocator.normalize` 只 trim、`squash` 只去空白，
**不统一括号** ⇒ 取备注字段时要自己处理（这是判定层的事，本增量不改）。

## 5. 结论与下一步

- ✅ `999 → 999`：**本次换引擎的唯一硬指标达成**，而且是最省的那种读法（rec-only，20ms）。
- ✅ 分数**数字本身**没有发现任何误读：现有 8 张（含两张 999）**8/8 全对**；剩下 10 张用户明确不测。
- ✅ 门槛已由用户收盘（2026-10-23）：余下 10 张不测；"25 行"是门槛写错（一屏行数有上限）。
- 🟡 **唯一没闭合的**：耗时是桌面 x86 fp32 测的，交付引擎不是这套 ⇒ 接真机后必须复测。
- 📌 接入形态（本次测出来的，写进 §7 步骤 3）：**两条路都走「不跑 det、直接 rec」**——
  分数块（区域已知，det 白花 60ms）与好友/区服名字（按行带切，§4.2 实测 20ms/行且没有并名问题）。
  det 只在"不知道文字在哪"的地方才有价值；这两处的区域/行带判定层本来就有 ⇒ **det 模型不用捆进包**
  （体积与包体账因此比 §4.2 的估算乐观得多）。
