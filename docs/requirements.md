# MasterMechanic 需求文档

> 本文档描述 MasterMechanic 要实现什么，全文只回答「程序应在什么条件下做什么、怎么算做成了、失败时如何收场」。
>
> 采用哪种画面感知手段、哪种输入注入途径、参数取什么值，由实现者自行研究并验证，但必须满足 §5 的要求。

---

## 1. 目标

### 1.1 要解决的问题

玩家在《王者荣耀》的王者农场里有两类反复动作，程序要替他消掉：

| # | 痛点 | 期望 |
| --- | --- | --- |
| 1 | 活动弹窗反复出现，必须手动关掉 | **自动处理，看到就消掉** |
| 2 | 有多个不同区服的小号，要挨个切过去、进农场、拜访指定好友 | **配置一次，一键自动跑完全部账号** |

第 2 类是本项目的核心。手动完成一个账号需要「退出农场 → 退出登录 → 换区 → 选择服务器 → 登录游戏 → 进入农场 → 打开好友列表 → 拜访指定好友的农场」整整一串操作，账号多了就是大量重复点击。

### 1.2 两种工作模式

| 模式 | 说明 | 谁发起 |
| --- | --- | --- |
| 常驻守护 | 自动关闭活动弹窗，长期在后台待命 | 程序自主 |
| 一键巡查 | 按配置依次切换各区服小号，逐个进入指定好友的农场 | 用户点击一次按钮 |

两种模式都要求：**游戏不在前台时，一律不识别、不点击。**

### 1.3 前提与范围外

| 项 | 说明 |
| --- | --- |
| 系统 | Android 9.0 及以上，**不需要 root** |
| 授权 | 画面采集与输入模拟的授权由用户在系统层面自行授予，可随时撤销；缺失时必须明确提示，不得静默失败 |
| 屏幕 | 尺寸与密度由用户设备决定，程序**不得绑定任何具体分辨率或密度** |
| 不涉及 | 不读取游戏内存、不注入游戏进程、不修改或拦截网络、不篡改客户端 |
| 不涉及 | 不输入任何账号凭据。巡查切换的是**同一登录账号下的不同区服**，不涉及登录账号本身的切换 |
| 不涉及 | 本版本不实现「祝福」逻辑（到达指定好友的农场即算完成，见 §7） |
| 账号前提 | **投入使用的账号须先完成至少一局对局**：完成后新手引导 / 新手大厅不再出现，本版本因此不处理这两个界面（2026-09-13 用户口径，见 §3.1 说明） |

## 2. 界面状态

### 2.1 状态清单

程序需要能分辨下列界面。「界面标志」指页面上可被辨认的稳定视觉元素；识别以「界面上是否存在该标志」为单位。

| 状态 | 判定依据（界面标志） | 常驻守护下 | 巡查流程下 |
| --- | --- | --- | --- |
| 启动页 | 「开始游戏」「换区」 | 等待 | 执行换区、登录 |
| 服务器列表 | 「选择服务器」 | 等待 | 选择配置指定的区服 |
| 大厅 | 对战 / 排位 / 农场入口（任一命中即为大厅） | 等待 | 进入农场 |
| 农场 | 农场标志 | 等待 | 打开好友列表 |
| 好友列表 | 好友列表标志 | 等待 | 定位并拜访目标好友 |
| 好友的农场 | 拜访后进入的农场 | 等待 | 视为该账号完成 |
| 活动弹窗 | 弹窗关闭控件（需覆盖多种样式） | **自动关闭**（任何阶段，见 FR-01） | **自动关闭**（任何阶段，见 FR-01） |
| 未知 | 以上均不命中 | 不操作，提示用户 | **暂停并提示用户** |

### 2.2 状态稳定性

状态切换不得由单次识别结果驱动：**连续 2 次**命中才进入该状态，**连续 3 次**未命中才离开该状态，连续 3 次未命中任何标志才判为未知。

进入与退出用不同阈值，用于抑制画面抖动导致的误判。

## 3. 功能需求

### 3.1 自动异常处理

这两类是程序自主执行的，不需要用户发起。

#### FR-01 活动弹窗自动关闭

| 项 | 内容 |
| --- | --- |
| 触发 | **任何阶段**每轮**最高优先级**，先于该阶段的其他识别。弹窗自点击「开始游戏」之后出现（FR-04 第 6 步起）；**实测其出现可延续到进入大厅之后**（2026-09-13），故不受阶段限制，**常驻守护待命期间同样检查** |
| 做什么 | 识别弹窗的关闭控件并点击；必要时辅以「关闭」「跳过」等文字标志 |
| 搜索范围 | **仅屏幕右上角局部范围**，不得全屏搜索 |
| 成功判据 | 弹窗**不再出现**即视为完成（连续数轮未命中）。**不逐次判定"单次点击是否奏效"**——实测表明「点击后仍命中」无法区分「弹窗没关掉」与「换了一个新弹窗」（2026-09-13 真机） |
| 失败处理 | **同一段弹窗内点击次数设上限**：达到上限即停止点击并记录，弹窗消失后复位。该上限只用于兜底「**锚点未命中关闭控件**」（宁可漏关，不可错点），**不作为单次点击的成败判据** |

> 弹窗遮挡画面、阻断全部识别，且关闭控件位置固定、后果可逆，因此是唯一允许「看到就点」的一类。

> **FR-02（新手引导 / 新手大厅自动返回）已于 2026-09-13 由用户决定移除，本版本不实现。**
> 依据：账号完成一局对局后这两个界面不再出现，投入使用的账号可先手动过掉（见 §1.3「账号前提」）。
> 因此 §2.1 不再包含新手大厅 / 新手引导状态，§4 的可点击来源也收窄为 FR-01 一类。
> 恢复条件：若后续出现无法先打完一局的账号（全新号），需重新评估是否恢复本条。

### 3.2 小号巡查（核心功能）

#### FR-03 巡查配置

用户在前台界面中配置巡查列表，配置需持久化（重启后仍在）。

| 项 | 说明 |
| --- | --- |
| 巡查项 | 每项 = **一个区服名称 + 一个目标好友名称** |
| 顺序 | 按列表顺序依次执行 |
| 校验 | 区服名称与好友名称均不得为空 |
| 重复 | 允许同一区服重复出现（例如同一区服拜访多个好友） |
| 编辑 | 支持增、删、改、调整顺序、整体清空 |

#### FR-04 巡查主流程

用户点击「开始巡查」后，程序对配置中的每个巡查项**依次**执行下列步骤。

**每一步都必须在执行动作后验证结果，验证通过才进入下一步。**

| # | 步骤 | 做什么 | 进入下一步的验证 | 未通过时 |
| --- | --- | --- | --- | --- |
| 1 | 起始确认 | — | 当前处于**启动页、服务器列表、大厅、农场或好友的农场**任一（**起点决定从第几步开始**，见下表） | 中止并提示 |
| 2 | 退出农场（**仅起点为农场 / 好友的农场时**） | 点击农场内的返回 / 退出入口 | 场景变为大厅 | 停 3 次后中止 |
| 3 | 退出登录 | 进入游戏内的退出登录入口，点击并确认 | 场景变为启动页 | 停 3 次后中止 |
| 4 | 换区 | 点击「换区」 | 场景变为服务器列表 | 停 3 次后中止 |
| 5 | **选择区服** | 在服务器列表中查找**配置指定的区服名称**并点击 | 场景离开服务器列表、回到启动页 | 找不到即中止，不做猜测性点击 |
| 6 | 登录游戏 | 点击「开始游戏」；其间出现的活动弹窗按 FR-01 逐个关闭（可能出现 **0 个 ~ 多个**） | 场景变为大厅 | 停 3 次后中止 |
| 7 | 进入农场 | 点击「王者农场」入口 | 场景变为农场 | 停 3 次后中止 |
| 8 | 打开好友列表 | 点击农场内的好友入口 | 场景变为好友列表 | 停 3 次后中止 |
| 9 | 拜访好友 | 在列表中定位**配置指定的好友名称**并点击拜访 | 确认已进入该好友的农场 | 停 3 次后中止 |
| 10 | 本项完成 | **停留当前界面，不做任何返回动作**：到达好友的农场即完成辅助操作 | —（无动作，无需验证） | — |

全部巡查项执行完毕 → 停止巡查并提示用户。

**起点 → 起始步骤**（第 1 步命中哪个画面，就从哪一步开始）：

| 起始画面 | 从第几步开始 | 说明 |
| --- | --- | --- |
| 好友的农场 / 农场 | 第 2 步 | 需先退出农场 |
| 大厅 | 第 3 步 | 大厅没有农场退出入口 |
| 服务器列表 | 第 5 步 | 已在选服页，不必再点一次「换区」 |
| 启动页 | 第 4 步 | 统一从「换区」开始（多一次换区，但不会走错） |

> **弹窗的处理贯穿整个登录环节**：可能 0 个，也可能连续多个，逐个关闭。
> **弹窗的出现不以保证「已进入大厅」为前提**：实测（2026-09-13）弹窗可在大厅出现**之后**才弹出；因此第 6 步验证通过（场景变为大厅）之后、第 7 步动作之前，仍需按 FR-01 检查并关闭弹窗。
>
> **第 10 步之后本项即结束**，程序不要求回到某个特定界面：用户手动完成「祝福」后自行发起下一次切换小号。
> 下一次的起点可能是自己的农场或好友的农场，两者的「切换小号」操作路径一致。
>
> **大厅发起 = 农场发起流程的子集**（2026-09-13 用户确认）：起点已是**大厅**时，第 2 步不适用（大厅没有农场退出入口），
> 直接从第 3 步「退出登录」开始；此后与农场发起**完全重合**。因此「大厅 → 切换小号」只是本表从第 3 步起的部分，
> 不构成一条独立流程。

**三种执行区间**（2026-09-13 用户确认）：用户可选择流程的**终点**，从而只执行本表的一个区间；**起点仍由第 1 步确认**。

| 场景 | 起点 | 终点 | 执行区间 |
| --- | --- | --- | --- |
| 换号 + 拜访 | 启动页 / 服务器列表 / 大厅 / 农场 / 好友的农场 | 好友的农场 | 起点所在步 → 第 10 步 |
| **只换号** | 启动页 / 服务器列表 / 大厅 / 农场 / 好友的农场 | **大厅** | 起点所在步 → 第 6 步（第 6 步验证通过即停） |
| **只拜访** | 大厅 / 农场 / 好友的农场 | 好友的农场 | 第 7 步 → 第 10 步（跳过全部换号步骤） |


**流程中的硬性要求**

| # | 要求 |
| --- | --- |
| 1 | **每一步都要验证。** 动作执行后必须确认画面已变成预期状态，才允许执行下一步。不得连续盲点 |
| 2 | **验证不通过就停。** 不满足前置条件时直接中止并提示，不做「试试看」式的点击 |
| 3 | **服务器列表与好友列表必须按名称精确定位。** 名称不唯一、或与配置不一致时视为未找到 |
| 4 | **服务器列表需要滚动时**，逐屏滚动查找；滚动次数设上限，超出即中止并提示（见 §7） |
| 5 | 单步失败重试不超过 3 次，超过即中止整个流程 |
| 6 | **中止后不自动重试整条流程**，必须由用户决定如何继续 |
| 7 | 巡查期间暂停常驻守护的自动动作，两者不得同时下发点击 |
| 8 | 每一次点击之间的间隔不低于 300ms |
| 9 | 巡查期间游戏离开前台 → 立即中止当前动作并暂停巡查（见 FR-09） |

#### FR-05 巡查的中断与恢复

长链条必然会中断（验证码、网络卡顿、临时弹窗、用户切走）。中断后必须让用户能低成本接上，而不是从头再来。

| 情形 | 程序行为 |
| --- | --- |
| 任一步骤验证不通过 | 停止动作，在悬浮窗中显示**停在哪个账号的哪一步、什么原因**，等待用户处理 |
| 场景变为未知 | 同上；**不点击任何东西** |
| 游戏离开前台 | 立即停止动作并暂停；回到前台后不自动继续，等用户确认 |
| 用户点「继续」 | **从失败的那一步重试**，不重跑前面的步骤 |
| 用户点「跳过此项」 | 放弃当前巡查项，直接从下一项的起始确认开始 |
| 用户点「停止巡查」 | 立即停止，回到常驻守护模式 |

#### FR-06 巡查记录

| 项 | 说明 |
| --- | --- |
| 实时显示 | 悬浮窗显示当前进度：第几个巡查项 / 共几个、当前在第几步 |
| 结果记录 | 每个巡查项结束后记录：区服名称、目标好友、成功或失败、失败步骤与原因 |
| 可回溯 | 每次点击都能对应到一条识别记录（命中了什么、位置、置信度），用于事后核对有没有点错地方 |
| 全部完成 | 给出汇总：成功几项、失败几项及原因 |

### 3.3 运行支撑

#### FR-07 悬浮窗与操作菜单

| 项 | 说明 |
| --- | --- |
| 展示 | 常驻半透明标签，显示当前状态与当前动作（如「状态：农场 / 拜访好友」），**必须触摸穿透**，不得拦截游戏操作 |
| 交互 | 收起态为一个紧凑手柄；单击展开菜单（单击只展开，不执行任何操作） |
| 菜单项 | 文案随模式变化：待命时为「开始巡查」；巡查中为「继续」「跳过此项」「停止巡查」 |
| 尺寸 | **紧凑到只包住内容**。悬浮窗会吞掉其覆盖范围内的触摸，铺满将导致游戏无法操作 |
| 拖动 | 按住手柄可移动，位移超过系统触摸滑动阈值才算拖动（不得用「位移是否非零」判断，手指抖动会导致永远展不开菜单） |
| 贴边 | 拖动结束后吸附到最近的屏幕边缘，大部分移出屏幕、仅露出约 40% 宽度；位置需持久化，且始终可被找回 |
| 收起时机 | 操作成功结束后立即收起；失败时保持展开并显示原因 |
| 可见性 | **仅游戏在前台时可见**，非前台时完全消失（既不可见也不占触摸），回到前台后以收起态恢复 |
| 不干扰 | 悬浮窗的可见性、位置、展开状态**不得改变识别结果** |

#### FR-08 后台运行

| 项 | 说明 |
| --- | --- |
| 常驻 | 识别与巡查必须在后台持续运行，不依赖前台界面存活；切后台、熄屏不被系统中止 |
| 通知 | 服务在系统通知中可见，用户能据此确认程序正在运行 |
| 授权 | 关键授权必须由用户在前台界面中主动确认，不得由后台静默发起 |
| 提示 | 授权状态与运行状态必须展示，避免出现「什么都不发生」的沉默失败 |

#### FR-09 前台判定

| 项 | 说明 |
| --- | --- |
| 判定对象 | 目标应用是否位于前台 |
| 独立信号 | 必须是**独立判定**，不能以「没有识别到任何标志」代替——加载页、黑屏同样识别不到标志，二者是两件事 |
| 判定失败 | 无法取得前台信息时，一律**按非前台处理**：隐藏悬浮窗、停止一切操作、中止巡查并提示。宁可停住，不可乱点 |
| 生效延迟 | 前台状态变化后 2 秒内生效 |
| 作用 | 非前台时不点击；非前台时中止巡查；非前台期间不消耗 §2.2 的连续计数（否则重新登录时跳转外部授权会被凑满「连续未命中」而误判失败） |
| 会话区分 | 「用户切到别的应用」只隐藏悬浮窗、停止操作，回来自动恢复；「采集会话终止」（用户主动停止、锁屏、进程被回收）才停止循环并引导重新授权。二者混淆会变成「切走一次就要求重新授权」 |

## 4. 关键约束

**能点什么**

1. FR-01 活动弹窗自动关闭，一类异常处理。
2. §3.2 巡查主流程中明确定义的步骤。
3. 用户通过悬浮窗菜单发起的操作。

**不能点什么**

| # | 约束 |
| --- | --- |
| 1 | 游戏不在前台时，**一律不点击** |
| 2 | 状态为未知时，**一律不点击**——界面不明时的「试探性点击」是最危险的行为 |
| 3 | 不点击巡查流程步骤之外的任何按钮（不领取奖励、不购买、不消费、不参与任何玩法） |
| 4 | 服务器与好友必须按配置指定的名称定位；**宁可停下也不用猜测的位置** |
| 5 | 常驻守护模式下，除 FR-01 外不产生任何点击 |
| 6 | 巡查与常驻守护的动作不得同时下发 |

**为什么第 4 条特别重要**：切换区服与拜访好友都涉及「在一堆外形高度一致的目标里挑一个」。挑错的代价不可逆（进错区服、打扰错好友），因此定位必须由配置给定的名称唯一确定；名称匹配不唯一或找不到时，正确做法是停下，而不是挑一个最像的。

## 5. 识别能力要求

识别是本项目一切动作的前提。本节不规定怎么做，只规定结果必须满足什么。

| # | 要求 | 说明 |
| --- | --- | --- |
| 1 | 判定可审计 | 每次判定都要给出：命中了哪个标志、位置在哪、置信度多少、同一画面里最强的竞争位置是什么。用于事后核对「这次点击有没有点错」 |
| 2 | 不得只靠「分数最高」下结论 | 存在多处高分，或最高分与次高分差距过小时，判为**不可信**并按未识别处理 |
| 3 | 抗干扰 | 下列三种情况下不得误判：① 目标上叠了半透明遮罩；② 目标所在区域背景在动；③ 同一画面有多个外观相近的文字、图标或按钮而只有一个位置是目标 |
| 4 | 可复现 | 同一批画面数据、同一套参数，重复执行必须得到相同结果；参数调整后能对既有画面整体重跑并比对 |
| 5 | 设备无关 | 识别能力必须在**目标设备上自行建立**，不得硬编码任何与开发设备绑定的尺寸、密度、位置或阈值；更换设备后重建，指标不得下降 |
| 6 | 不受悬浮窗影响 | 悬浮窗开启或关闭、位置不同、展开或收起，同一画面的识别结果必须一致 |

**验收误报率时的口径**：负样本不少于 60 个；「零误报」必须以上界表述（n 个样本 0 次误报 → 真实误报率上界为 `1 − 0.05^(1/n)`）；三类干扰分别统计，不得合并成一个总通过率。样本不足时不得声称「零误报」。

> 第 3 类干扰是本项目的重点考点：「选择区服」与「拜访好友」都要在一堆外形相似的目标里挑一个，正是干扰最严重的场景。

## 6. 非功能需求

| 编号 | 要求 | 验收要点 |
| --- | --- | --- |
| NFR-01 | 单帧处理耗时 < 20ms | 真机连续 100 帧统计，P95 小于 20ms |
| NFR-02 | 检测间隔自适应：**需要响应时 ≤ 0.2s**（未达预期 / 画面变化 / 刚转移），**确实稳定时 ≤ 1s**。间隔指**两轮之间的休息时间**（单轮处理耗时不计入） | 稳定挂机时资源占用显著低于固定短间隔轮询；快档下「预期出现 → 确认」≤ 0.5s，与人工「看到界面 → 点击」的 200 ~ 400ms 同量级（且受 FR-04 硬性 #8「相邻点击 ≥ 300ms」约束） |
| NFR-03 | 安装包 ≤ 25MB，兼容 Android 9.0+（重点验证 Android 14 及以上） | 发布包实测；各版本均能完成授权、识别、悬浮窗可见 |
| NFR-04 | 连续运行 30 分钟无崩溃，内存不持续增长 | 真机长跑观察内存趋势 |
| NFR-05 | 不得点击到非预期位置 | 日志核对：每次点击都有对应的识别记录与判据 |
| NFR-06 | 两次点击间隔不低于 300ms | 日志核对相邻点击的时间戳 |

> NFR-05 是最重要的一条：误点击的代价远高于漏识别。漏识别只是流程停住，用户可以补一步；误点击可能进错区服、打扰错好友，或触发游戏内不可逆操作。§4 的全部约束与 §5 的可审计要求都是为这一条服务。

## 附：实现建议与维护方式

**推进顺序（建议）**

1. 先做到「只识别、不点击」，并验证 §5 的识别能力可信。
2. 再做 FR-01 自动处理。
3. 最后接巡查主流程。

理由：识别不可信时，后面所有点击都建立在错误判断上。巡查是最长的链条，放在最后做，前面每一步都已被单独验证过。

**维护方式（供本仓库维护者阅读，不属于需求）**

- 本目录**不得出现实现手段**：算法名、库名、系统接口名、设备型号、分辨率与密度数值、素材文件名、脚本名、本机实测参数值。
