## 1. 为什么单开一个里程碑

现有 11 条需求（FR-01~FR-11）里，**所有动作都是"点一下"**：识别一个锚点 → 点它 → 验证画面换了。
祝福第一次需要**连续输入**：按住方向键让人物走、拖拽转视角、走几秒才知道到没到。

这带来三个本项目此前没有的问题：

| 问题 | 为什么以前不存在 | 现在为什么绕不开 |
| --- | --- | --- |
| **动作没有"完成"这一刻** | 点击是瞬时的，`dispatchGesture` 回调即完成 | 移动是一条持续几百毫秒的手势，"走够了没有"要靠**画面**回答，不能靠手势回调 |
| **动作改变识别目标的位置** | 点击后画面是"另一个界面" | 移动后**同一界面**里所有东西都平移了 ⇒ 锚点窗口、模板位置全部失效 |
| **没有可读的"我在哪"** | 流程靠界面标志判断状态，状态是离散的 | 农场里 24 个格子外观几乎一样，**只能靠交互控件的出没**判断"站没站进去"（边框会被作物挡住，见 §3.2） |

因此它不是"再加一条流程步骤"，而是**新增一类能力**。硬塞进 `PatrolFlow` 会让 10 步状态机长出一个"农场内子状态机"，
两边都难维护（见 §7 的挂载点选择）。

## 3. 判据设计（先写验收）

### 3.1 目标选择：靠站位，不靠识别

**目标格 = 人物当前所站的格子。** 这是本功能最重要的一个性质：

- 不需要识别 24 个格子、不需要给格子编号、不需要俯视图 / 小地图；
- **红线 3（名称定位必须唯一）天然满足** —— 站位在任何时刻都只有一个格子；
- 反过来说，"我在哪"成了唯一必须闭环的量，而它的反馈也是现成的：**祝福控件出现 = 进了格，消失 = 出了格**（见 §3.3）。

### 3.2 可祝福判据：只看祝福控件

| 情形 | 判据 | 处置 |
| --- | --- | --- |
| **可祝福** | 祝福控件呈**亮**（可点击态），且判定可信 | 点它 |
| **不可祝福** | 祝福控件呈**灰** | 不点（**不需要知道原因**：人物配额用尽 / 该农场 30 次用尽 / 该格满 3 次，一律不点） |
| **不可信** | 多处高分、或最高与次高差距过小 | 按不可祝福处理（红线 7） |
| **认不到控件** | 定位不到 | 不动作（可能站在空地、被面板挡住、或不在农场） |

**为什么把边框从判据里删掉（2026-10-28 真机截图驱动）**：用户给的这张图里，人物正站在苹果树那一格，
**整个格子被树冠盖住、根本看不到边框**，而右侧的「剩余 10」清清楚楚地亮着。
⇒ **边框会被 3D 物体遮挡，交互控件不会**（UI 永远画在场景之上）。
原计划的"双信号 + 一致性闸"因此作废 —— 不是"两个都用更稳"，而是"**边框根本没资格当信号**"。

**为什么不需要判"可交互"这个中间概念**：两个控件的亮灰组合只是同一事实的另一种说法。
我们只对祝福有兴趣 ⇒ **它亮就点，它灰就不点**。拿取控件亮而祝福灰时，什么都不做（§4 只点祝福控件）。

**为什么不用左侧面板的 `n/3` 当主判据**：面板内容随情况变（未成熟显示倒计时、成熟显示可收获、还叠加变异标签），
OCR 读到的行数和位置都不稳定；`n/3` 只用来**验证祝福是否生效**（见 §3.4）。

**只在他人农场才会命中祝福控件** —— 这条让"不判农场归属"成为可能：
在自己农场里认不到祝福控件 ⇒ 不动作 ⇒ 不会误浇水/误收获。
（2026-09-23 用户拍板"不做农场归属判定"因此**不需要回退**，见 §8。）

#### ⚠ 唯一的真风险：亮 / 灰在 NCC 下可能分不开（2026-10-28 离线量测）

用户提供的两张按钮裁剪图（同一控件、两种状态）实测：

| 状态 | 尺寸 | 平均亮度 | 平均饱和度 |
| --- | --- | --- | --- |
| 高亮 `image.06aabf9095.png` | 76×80 | **144.1** | 0.313 |
| 灰色 `image.13644b33b9.png` | 68×80 | **103.4** | 0.307 |

差别**几乎全在亮度**（≈×0.72），饱和度没变（0.313 vs 0.307）。而现有匹配器是
**归一化互相关（NCC），分数对亮度 / 对比度归一化（±线性变换不改变结果）**
（`recognition/TemplateMatcher.kt` 类注释）⇒ **同一个模板对"高亮"和"灰"可能给出几乎一样高的分数**。

⇒ **M7-1 的第一个验证点不是"能不能点"，而是"能不能分清"**：真机上各采一帧（可祝福 / 不可祝福），
用现有匹配器离线跑，记录"高亮模板 × 灰帧"的 best 分数：

- **< 命中线 0.85** ⇒ 单模板二分类成立，照原计划（命中 = 可祝福，未命中 = 不动作）；
- **≥ 0.85** ⇒ NCC 这条路**不可用**，必须补一种**不受亮度归一化影响**的判据。首选：
  **在同一个标定窗口内统计平均亮度**，分界取两条"标定基线"的中点（标定时分别采亮态 / 灰态各一帧）
  —— 阈值仍由设备自己产生，不违反红线 4。

> ✅ **2026-10-28 当日已用真机证伪**（[farm-bless-research.md](../recognition/farm-bless-research.md) §2）：
> 同一 UI 位置、**同一格作物**，**亮态 `meanL 192.1` / 灰态 `127.8`（差 +64.3，比值 1.503；
> 窗口取图标本体、半边长 40px）** ⇒ **NCC 单模板二分类不成立**，判据形态按上表定案。
> 窗口越小越可分（150px 时差只剩 +18.6）⇒ **标定必须框图标本体**。
> 实测中点 `≈159.9` **只作参考、不入代码**（红线 4：阈值必须由目标设备自标定）。

**这个风险有一半被同一个性质抵消（也顺手定下了判据形态）**：NCC 对亮度免疫 ⇒ 灰色按钮**仍然会被
"祝福控件模板"高分命中**。所以两件事必须**分开判**，各用各的工具：

| 要判什么 | 用什么 | 亮 / 灰都能判吗 |
| --- | --- | --- |
| 控件**在不在**（= 站没站进格子，§3.3 的到位信号） | 模板匹配（NCC） | ✅ 能 —— 这正是 NCC 的长处 |
| 控件**亮不亮**（= 能不能祝福） | 标定窗口内的**亮度统计** | ❌ 只有亮度统计能分 |

⇒ **M7-1 的判据形态至此确定**：模板匹配负责"到没到位"，亮度统计负责"能不能点"。
NCC 只可能在第二个问题上失手，而第二个问题本来就不该由它回答。

### 3.3 移动：每一步都必须验证（红线 5 在连续动作下的落法）

移动没有"完成回调"可用，因此**把每一步都定义成"短推 + 观察"**，而不是"按住走 3 秒"：

```
推一次（固定方向、固定时长）
  → 等画面稳定（帧龄 / 连续两帧一致）
  → 看祝福控件在不在：定位得到 = 站在某个格子里；定位不到 = 在空地上
  → 在格子里再看它亮不亮：亮 = 可祝福（交给 §3.4）；灰 = 换方向继续走
  → 才决定下一次推的方向与时长（不在格子里 ⇒ 继续朝地块方向推）
```

**到位判定用"祝福控件的出现 / 消失"**，既不是"位移像素"，也**不是边框**：
3D 场景没有稳定的位移参照物；边框又会被作物遮挡（§3.2）；
而祝福控件"人在格子里就出现、人在空地就消失"，是三者里唯一**不受 3D 遮挡影响**的到位信号。

⚠ **已知边界**：如果站的那一格两种操作都不可（橙框那种），祝福控件**仍然是灰的、但仍然在**——
所以"在不在"与"亮不亮"必须分开判：前者用来知道"到没到位"，后者用来知道"能不能点"。
**不能**把"控件是灰的"当成"没到位"，否则会在到达之后一直往前走。

**力度是第二个自由度，而且比"极短时长"更可靠**：摇杆是浮动摇杆且**力度连续可调**
（死区 20~25px、满推 200px，见 [研究文档](../recognition/farm-bless-research.md) §4）。
想"走一小步"时，**用小力度 + 正常时长**（如 60~80px / 400ms），而不是"满推 60ms" ——
后者紧贴死区、帧调度一抖就变成"没动"或"冲出去"，而前者稳定得多。

**禁止**：
- 移动过程中下发任何点击（画面在动，识别结论不可信）；
- 一次长按跨越两个以上格子（跨格时中间那格会被整个跳过，等于盲穿）；
- 连续两次移动之间不读画面（等于盲走，违反红线 5 的精神）。

### 3.4 祝福动作与验证

| 项 | 口径 |
| --- | --- |
| 点击前 | 祝福控件**定位得到**（模板匹配）**且呈亮**（亮度统计，见 §3.2 末），并且不在"不可信"状态。否则不点 |
| 点击 | 只点**祝福控件**（不是右下角的「拿取」） |
| 点击后验证（任一成立即算成功） | ① 左侧面板 `n/3` 的分子 +1；② 屏幕「剩余 N」的 N −1 |
| 为什么不用"控件变灰"当验证 | 每格可祝福 **3 次** ⇒ 成功祝福 1 次后控件**通常仍然是亮的**；变灰只发生在该格满 3 次 / 该农场 30 次用尽 / 人物 10 次用尽 |
| 验证失败 | 不重试第二次（祝福可能已生效但没读到），**停下并如实报"点了但没验证到"** |
| 次数上限 | 单次执行内，**每格最多点 1 次**（同一个格子连续点会浪费配额）；全局上限 = 当天剩余次数 |

⚠ **`n/3` 与「剩余 N」都要走整屏读数**，而整屏 OCR 会读到我们自己悬浮窗上的文字（现有口径：读整屏时悬浮窗让开，
见 FR-07「口径修订六」⑤）。

### 3.5 结束条件（必须同时满足"不无限点"与"该走完的要走完"）

按优先级：

1. **配额用尽**：屏幕「剩余 N」读到 0（或 M7-1 阶段无法读到 ⇒ 用"连续 10 次成功"兜底）；
2. **扫完两块地且无新增可祝福格**：一整块地按行推满一遍，没有出现新的"控件亮"的格子；
3. **用户点停止**；
4. **任一验证失败 / 状态离开农场 / 未知**；
5. **单次执行时间预算**（初定 180 秒，实测后调）。

**已确认的两条规则（2026-10-28 用户回答，不必再测）**：

- **橙框那种情况的原因**：该农场已达**当日被祝福上限（30 次）** ⇒ 该农场的祝福控件全灰。
  **原因不用判别**（人物 10 次用尽 / 农场 30 次用尽 / 该格满 3 次，一律按"灰 = 不点"处理）。
- 「剩余 N」**跨农场共享**（人物那 10 次是一份，走到哪个农场都用它）。

> 这两条解释了"同为 `0/3`、同为可收获的两格为何一亮一灰"，也再次说明
> **判据不能建立在"是否成熟"或"`n/3` 是否用满"上** —— 只能看控件的亮灰。

## 6. 红线影响（**必须逐条落定才能写代码**）

| 红线 | 现在怎么写的 | 祝福带来的变化 | 处理 |
| --- | --- | --- | --- |
| 2 点击来源 | 三类：FR-01 / FR-02、主流程步骤、**用户经悬浮窗菜单发起的操作** | 祝福**属于第三类**（菜单发起）⇒ **红线 2 不用改** | ✅ 只需在 FR-11 里点明"从菜单发起"。⚠ 但"移动"是**连续手势不是点击** ⇒ 需补一句：**连续手势与点击同等受门禁约束**（守护/前台/未知/越界），否则移动会成为绕过门禁的后门 |
| 4 视觉零硬编码 | 一切阈值来自目标设备自标定 | 新增：**轮盘圆心/半径、拖拽距离**也是设备相关量 | ⚠ 标定页新增一组「农场控制」标定项（§7） |
| 5 动作后必验 | 点击后必须看到预期画面 | 移动没有"预期画面"，只有"**祝福控件的出现 / 消失**" | ✅ 已写进 FR-11「到位判据」：不得用"推了几次"当到位 |
| 6 间隔 ≥300ms | 从上次手势**完成**起算 | 移动手势可能持续 1s，间隔从"抬手"起算仍然成立 | ✅ 现有 `MIN_SPACING_MS` 口径不变，无需改 |
| 7 识别不可信 | 多处高分 / 差距小 ⇒ 按未识别 | 判据收成**单信号**后，交叉核对没了，只剩"同一控件多处高分 / 最高与次高太近"这一道 | ⚠ 已写进 FR-11：不可信 ⇒ 按不可祝福处理。**这是单信号设计的代价**：模板一旦把别的图标误认成祝福控件，没有第二个信号兜底 ⇒ 标定窗口必须收紧到控件附近 |

## 7. 落点（实现侧，供后续裁决）

| 要新增的 | 放哪 | 为什么 |
| --- | --- | --- |
| 长按 / 持续手势语义 | `action/ClickModels.kt` + `GestureInjector` + `ClickForwarder` | 唯一手势出口不许绕开；`SwipeRequest` 语义是"滑动"，摇杆需要"按住 N 毫秒" |
| **亮 / 灰判据**（**必需**，见 §3.2 末） | `recognition/` 新增"标定窗口内亮度统计" | 现有只有 `RgbaToGray`（整帧转灰度）与 `FrameUniformity`（整帧判纯色），没有"在某个窗口里算均值"的工具。**注意：不需要 HSV / 边框颜色识别** —— 判据已收成按钮的亮灰 |
| 祝福会话 | 新增 `bless/` 包（与 `patrol/` 并列） | **不塞进 `PatrolFlow`**：那是一张 10 步表，加子状态机会把两边都搞浑（§1） |
| 菜单入口 | `floating/FloatingWindow` 一级项 | 红线 2 第三类 |
| 新标定用途 | `patrol/PatrolAnchors`（用途是字符串契约，不是枚举） | 沿用现有标定产物格式：新增 `farm_bless_button`（M7-1）与 `farm_joystick`（M7-2）。**不再需要 `farm_cell_border`** —— 边框不是判据 |

## 8. 明确不做

| 不做 | 理由 |
| --- | --- |
| 浇水 / 收获 / 拿取 | 用户只要求祝福；且这三者是**不同的控件**，逐个加会变成"农场全家桶" |
| 判农场归属（这是谁的农场） | 2026-09-23 已拍板不做；只认祝福控件即可保证不误动作（§3.2） |
| 给 24 个格子编号 / 建地图 | 站位即目标，编号没有任何用处（§3.1） |
| 自动识别"哪一格最值得祝福" | 那需要理解作物价值，属于策略层，不是自动化层 |
| 无人值守挂机祝福 | 与"一次执行只跑一趟"的既有产品口径一致（§1.1）；挂机也会显著提高被判定为脚本的风险（ADR-002 同源） |
| 用俯视图 / 小地图导航 | 游戏内没有这个界面（用户给的俯瞰图是玩家自截） |
