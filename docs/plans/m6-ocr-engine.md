> 立牌那条线改**混合**：名称 ML Kit、只有分数走 Paddle rec。
> **本文以下内容全部是"当时为什么这么想、量到了什么"，不再代表当前实现**，保留仅作决策记录与反面教材
> （尤其 §4.7：为 rec-only 追平 ML Kit，先后做了批量、指纹、裁窄、几何判顶四刀）。

> 状态：~~计划 / 待离线验证~~（2026-10-23 起）→ **2026-10-24 回退**
> 触发：临时需求封板前的一次真机 bug —— 花体数字 `999` 被 ML Kit 稳定读成 `666`。
> 关联：`m6-nfr-hardening.md`（NFR-01 耗时 / NFR-03 包体）、`temp-badge-share.md`（立牌流程）。

## 1. 为什么要换（问题不是参数，是模型）

真机实证（2026-10-23，`奇迹瀑布` 区服「蒙犽顶级立牌」）：

| 事实 | 证据 |
| --- | --- |
| 画面确实是 999 | 设备截图 + 按产物窗口 `(1087..1183, 912..962)` 裁切放大，字形清楚是三个 9 |
| 区域没框错 | 同一块区域读出的**分享码 `UZQ5PN` 完全正确**，名称只差一笔 |
| 不是抖动 | 两次读数**一致**都是 `666` ⇒ 「两次一致才落盘」挡不住系统性误读 |
| 调参无效 | 灰度 ×3 与 二值化 ×6 两版路径都得到 `666` |

结论：**这是模型对这套花体数字的判读偏差（9 与 6 同形，转 180°）**，不是阈值/放大/二值化能救的。
`904` 里的 9 又能读对 ⇒ 不是"所有 9 都错"，而是特定字形。这类问题只能换识别器（或做模板匹配）。

## 2. 范围

- ✅ 替换 `NameReader` 的**实现**（引擎层）：好友名称、服务器名单、大厅昵称、立牌三块文字、分数；
- ❌ **不动**判定层：锚点契约 / 行带 / 左右列顺序 / 消歧规则 / 两次读数一致的口径全部保持；
- ❌ **不做**云端 OCR（离线、隐私、无网络可用性都不过关）；
- ❌ 不做"专门给数字写一套模板匹配"（用户已定：直接上 PaddleOCR）。

## 3. 先决门槛：离线验证（不过就停）

**在动依赖之前**，用 Python 版 PaddleOCR 跑真机原图（`adb screencap` 拿 3168×1440，**不经压缩**）：

| 用例 | 通过线 |
| --- | --- |
| `999` 那张分数区 | 必须输出 `999`（这是本次换引擎的唯一硬指标） |
| 其余 16 张分数（用户提供的真值：904/330/589/115/575/111/349/326/545/233/774/607/256/871/660/904） | 三位数字全对 |
| 好友列表一帧（**一屏所见行数**） | 名字行不串行、不漏行 |
| 服务器列表一帧（左右列） | 左列 7 行 + 右列 7 行按序读出 |
| 单块耗时 | 分数块 ≤ 300ms；整屏一屏名字 ≤ 1000ms（与现口径同级） |

> **2026-10-23 用户更正**：原门槛写"25 行"是错的 —— **好友列表一屏能显示的行数有上限**，不存在 25 行的画面。
> 门槛按"**一屏实际行数**"算（现有生产尺度帧是 5 行）；「整屏 25 行 ≤1000ms」同理。

**任何一项不过 ⇒ 停在这里，不引入依赖**，回来再评估模板匹配或拉丁模型。

### 3.1 验证结果（2026-10-23，`stage/m6`）

| 用例 | 结果 |
| --- | --- |
| `999` 分数区 | ✅ **`999`，置信度 1.0000**（产物窗口 96×50 rec-only 20ms；整帧 det+rec 同样读到 999；另有第二张 999 独立重现） |
| 其余 16 张分数 | ✅ **已到的 7 张全对**（`589/115/575/326/774/607/999`）；**用户 2026-10-23 定：余 10 张不用测** |
| 好友列表（一屏 5 行） | ✅ 按序、不串行、不漏行（**det 路径会并进等级数字、且错低频字** ⇒ 见下） |
| 服务器列表左右列 | ✅ 旧帧池 6+6：左右列 x 分明、按序、区服名逐字正确 |
| 单块耗时 | ✅ 分数块 20ms / 批量中位 45ms / **按行带 rec-only 20ms 一行** |

**⇒ 门槛通过。** 但测出两件必须在接入时一并解决的事（详见证据文档 §4）：
① **det 路径不可用**：整屏 det+rec 桌面就 2.1~3.1s（≈ 框数 × 30~55ms），且会把等级数字并进名字、低频字认错；
② **跳过 det、按行带直接 rec** 两者都解决（20ms/行，`Boss~~喵（阿娜雅)` 干净读出）。
⇒ 接入形态应是 **rec-only**（分数块 + 名称行带），这样也把"要不要 det 模型"这笔体积省掉了。

详细数据、环境与脚本见 [`../verification/m6/t6-1-ocr-offline-gate.md`](../verification/m6/t6-1-ocr-offline-gate.md)。

## 4. 依赖评估（待用户确认）

### 4.1 硬约束

- **包体 NFR-03：≤ 25MB**（`m6-nfr-hardening.md` §2）。当前 release **16.48MB**（只打 `arm64-v8a`，
  见 `app/build.gradle.kts` 的 `abiFilters`）⇒ 新增预算 **≈ 8.5MB**（含 native 库 + 模型 + 代码）。
- 无 Google Play（国行 vivo）⇒ 只能**捆绑**模型，不能按需下载；
- OCR 现在是**帧线程同步调用**（`MlKitNameReader` 上限 1s）⇒ 新引擎必须给出同等或更好的单轮上限，
  超了就得异步化，那是另一笔改动。

### 4.2 候选

| 方案 | 模型体积（估） | native | License | 备注 |
| --- | --- | --- | --- | --- |
| **ncnn + PP-OCRv4 mobile**（推荐先验） | det ≈4.7MB + rec(ch) ≈9.9MB（**int8 量化后 rec ≈5MB**） | libncnn.a arm64 ≈2~3MB | ncnn BSD-3 / PaddleOCR Apache-2.0 | 体积可控；Android demo 成熟；中文效果好 |
| MNN + PP-OCR | 同上 | libMNN ≈2~3MB | Apache-2.0 | 与 ncnn 同级，选一即可 |
| onnxruntime-android + PP-OCR onnx | 同上 | AAR 含 4 ABI ≈10~16MB（可只留 arm64） | MIT | 集成最省事但体积最大，**大概率超预算** |
| ML Kit **拉丁**（`text-recognition`） | +几 MB | 已有 OCR pipeline（同一 `.so`） | ML Kit 条款 | 与中文同一引擎家族，**不保证** 9/6；只能做"数字专用第二通道"对照 |
| Tesseract（`chi_sim`） | 字库 20MB+ | ≈3MB | Apache-2.0 | 体积与精度都不划算 |

### 4.3 预判

`ncnn + PP-OCRv4 mobile`，**det 保留 fp16、rec 用 int8**，并**去掉方向分类模型**（截图不旋转）：
`~4.7 + ~5 + ~3 ≈ 13MB` ⇒ **压不进 8.5MB 预算**。

因此本增量必须二选一，请用户拍板：

1. **放宽 NFR-03**（例如 ≤30MB）：理由是 OCR 是整条流程的眼睛，读错比包大危险得多；
2. **不动包体，只替换"分数"这一格**（不换整条 OCR）：仍是 ML Kit 为主，仅分数块用 Paddle 的 rec
   小模型（~5MB）+ 顶层 det 关闭（区域已知，直接整块喂 rec）⇒ 体积可压到 6~7MB。

> 我倾向 **方案 2 先落地**（先修掉让用户看得见的错，体积可控），等 M6 里 NFR-03 有结论再谈全量替换。

### 4.4 决定（2026-10-23，用户拍板）

**走方案 1：放宽包体，全量换引擎。**

- NFR-03 由 **≤25MB 放宽到 ≤32MB**（`m6-nfr-hardening.md` 已同步）：现状 16.48 + 新增 ≈13
  ⇒ 约 29.5MB，留 ~2.5MB 余量（模型升级 / 后续补丁）；
- 依赖定为 **ncnn（BSD-3）+ PP-OCRv4 mobile**：det 用 fp16、rec 用 **int8**、**不要方向分类模型**；
- **降级条件（写死，防止无限膨胀）**：真机实测 release 若 >32MB，或 rec 精度不达标，
  退回方案 2（只换分数），不靠"再放宽一点"解决；
- 仍然**不做**云端 OCR、不做数字模板匹配（用户已否决模板路线）。

### 4.5 运行时改判：ncnn → **ONNX Runtime**（2026-10-23）

用户确认「全部改为 Paddle」之后，按实测把运行时换了，理由三条：

1. **只需要 rec**（§3.1 结论：det 不要）⇒ 模型只有一份，ncnn 的优势（体积）不再关键；
2. **本机没装 NDK / CMake**（`%ANDROID_SDK%\ndk`、`cmake` 均不存在）⇒ ncnn 要额外下载工具链 + 自写 C++ JNI
   + 转 ncnn 格式；ORT 是一条 Maven 依赖 + Java API；
3. **体积实测下来是中性的**（数字见下）。

| 项 | 实测 |
| --- | --- |
| 依赖 | `com.microsoft.onnxruntime:onnxruntime-android:1.20.0`（`libs.versions.toml`） |
| 模型 | PP-OCRv4 mobile **rec**（fp32 ONNX 10.35MB，`assets/ocr/ppocrv4_rec.onnx`）+ 字符表 6623 字（26KB） |
| debug APK | 49.10MB → **59.18MB** |
| **release APK** | 16.48MB → **26.91MB**（此时 ML Kit 还没摘；摘掉它的 4.47MB 压缩后 ≈ **22.4MB**） |
| 打包口径 | `jniLibs.useLegacyPackaging = true`（`libonnxruntime.so` 16.76 → **6.49MB**）、`noCompress += "onnx"` |

⚠ **int8 量化没做成**：ORT 的 `quantize_dynamic` 在这份导出上直接报
`Expected conv2d_157.w_0 to be an initializer`（onnxsim 化简后同样）。**先用 fp32 落地**（体积够），
要压体积/提速再另开一刀（换导出器或做静态量化）。

### 4.7 真机性能打磨（2026-10-23，从立牌分支同步 8 笔 + 2 笔手工移植）

换引擎后"选服务器"这一步在真机比 ML Kit 慢，逐个瓶颈量过再改，累计效果：

| 阶段 | 不滑屏 | 要滑屏（第二屏） |
| --- | --- | --- |
| 刚换引擎（rec-only，26 行/轮） | 3.17~3.35s | 6.49~9.36s |
| + 几何判"已在顶点"（省 2 次空滑 + 3 次白读） | 1.77~2.04s | 4.26~5.59s |
| + 首读横向裁 45%（只认行首区号） | **1.43~1.56s** | **3.21~3.69s** |

各刀的判据与理由（都已落地，注释在代码里）：

1. **批量推理**：rec 一次只能读一行，但模型第 0 维动态 ⇒ 13 行一次 `session.run`（桌面 4 条 24.0ms → 20.7ms，真机省得更多）；
2. **画面指纹复用**：像素完全一致时复用上轮结果（判据是**像素**不是时间）；⚠ 由此引出一次真机 bug —— Miss 分支被饿死 ⇒ 不滑屏，已用"复用也允许下决定 + 800ms 决策节拍"修好；
3. **帧龄 >500ms 不读字**（兜底重放时白读 250ms、且 y 是旧的）；
4. **几何判顶**：最上行贴着列表上沿 ⇒ 已在顶部，不必用滑动去试；
5. **确认轮只读命中行窄带**（y±140px）；
6. **首读横向裁 45%**（`微信392区` 在行首）＋ 两重兜底（无数字 / 无「区」字 ⇒ 退回整列读）。

⚠ 走不通的两条（都有实测，别再试）：**int8 量化**（只量化 MatMul 0.97× 等于没快；全量化 2.75MB 但把 `589` 读成 `1589`）；**补 det**（桌面单列 det 就 197ms，真机 400~800ms/列，比现在还慢）。

⚠ **`stage/m6` 上没有"分数"的调用点**（`DigitReader` 那套在 `temp/badge-share-1021`）⇒ 本次换引擎在 `stage/m6` 只能先覆盖
**名称**两条路（第 5 / 9 步）。要让 `999` 真的被修好，得把引擎带到立牌流程那条分支上（合并或单笔 cherry-pick）。

## 6. 接入点与必须保住的契约

| 位置 | 现状 | 换引擎时的要求 |
| --- | --- | --- |
| `recognition/NameReading.kt` `NameReader` | `read(image, region) → List<NameCandidate>` | 新实现 `PaddleNameReader` 只是另一个实现，**接口不变** |
| `NameCandidate.text / x / y / width / height` | 坐标是**原帧坐标**（ML Kit 版本用 `/scale` 反算） | Paddle 的检测框必须换算回原帧坐标，否则行带/列精化全乱 |
| `DigitReader.readDigits` | 分数专用（二值化 + ×6） | 换成 Paddle 后可直接删掉这条通道（或保留作为回退） |
| `service/MlKitNameReader` | 生产实现 | **保留**，作为回退：初始化失败 / 模型缺失 / 超预算 ⇒ 自动退回它，日志写明原因 |
| `CaptureService` 调用点 | 好友名单 / 服务器名单 / 大厅昵称 / 立牌三块 / 分数 | 调用点不动，只换 `nameReader` 的注入 |
| 帧线程预算 | 同步调用，单次上限 1s（`DEFAULT_TIMEOUT_MS`） | 新引擎单次不得超过 1s；超过就要异步化（**本增量不做**，超了算不通过） |

## 9. 明确不做

- 不做云端 OCR；
- **不再找 ML Kit 的"方向开关"**（2026-10-23 字节码确认：捆绑中文识别器 `VkpTextRecognizerOptions.Builder` 只有
  `setLanguageHint / setConfigLabel / setModelDir / setEnableLowLatencyInBackground`，**没有方向/朝向参数**）；
  `InputImage.fromBitmap(.., rotationDegrees)` 是"这张图相对正立转了多少度"的元数据，不是"字朝哪"的提示，
  传 180 只会让引擎把整图转 180 再识别。**也不靠"转 180° 再读一遍"绕过 9/6 同形**：非回文数字（如 `904`）
  转 180° 会倒序换字，属"用错的方式读对一张"，无法推广；
- 不重写判定层（行带、列精化、消歧、两次一致）；
- 不为"数字"单独写模板匹配（用户已否决该路线）；
- 不在本增量里做 OCR 异步化（超预算就按不通过处理，另开任务）。
