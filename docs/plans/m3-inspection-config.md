## 范围边界

- **做**：
  - 巡查配置的**数据模型 + 校验 + 持久化 + 配置界面**（FR-03 全部条目）；
  - 悬浮窗**触摸口径修订**（收起态手柄必须可触摸才能"单击展开"）、**拖动判定**（按系统触摸滑动阈值）、
    **贴边吸附**、**位置持久化**、**展开态紧凑菜单**、**菜单动作出口**（发出"用户请求开始巡查"事件）、
    **收起时机**（成功收起 / 失败保持展开并显示原因）；
  - 「当前动作」展示位（字段与显示格式；内容由 M4 流程层写入）。
- **不做**：
  - **巡查主流程（FR-04）/ 中断恢复（FR-05）/ 巡查记录（FR-06）**——属 M4。M3 的菜单只把"用户请求"发出去，
    **不产生任何游戏点击**（红线 2：M3 不新增点击来源）；
  - 区服名 / 好友名的**名称定位与唯一性判定**（属 M4，`requirements.md` §4-4 / 红线 3）；
  - 性能达标（NFR-01 / NFR-02 未达标项移交 M5）；FR-08 加固（帧流静默停止检测等，后续里程碑）。

### T3-4 悬浮窗触摸口径修订 + 拖动 / 贴边 / 位置持久化

- 目标：把 `FloatingWindow` 由「整窗不可触摸 + 固定右上角」改为「**紧凑可触摸手柄** + 拖动跟手 + 抬手贴边 +
  位置持久化」。
- 验收：C3（紧凑 + 自身矩形外不拦截游戏触摸）/ C4（按系统触摸滑动阈值判拖动）/ C5（贴边吸附约 40% 露出 +
  位置持久化 + 尺寸变化后可找回）/ C8（非前台整窗移除回归）。
- 证据：拖动判定与贴边几何的**纯逻辑单测**（阈值判定 / 吸附计算 / clamp 与找回）+ 真机核对
  （用户执行：拖到四角 / 贴边 / 杀进程重启看位置 / 覆盖区点击穿透对比——复用 M0-T0-5 的"游戏静音图标切换"手法）。
- 实现要点（待确认）：
  - `WindowManager.LayoutParams` 去掉 `FLAG_NOT_TOUCHABLE`（保留 `FLAG_NOT_FOCUSABLE`），
    即**只有手柄自身矩形吞触摸**——这正是 FR-07「紧凑到只包住内容」的用意；
  - 拖动阈值取**系统 API**（`ViewConfiguration` 的触摸滑动阈值）的运行时值，不写常数（红线 4）；
  - 触摸事件到"是拖动还是单击"的判定放在**抬手时**裁决（超过阈值 = 拖动、未超过 = 单击展开），
    避免"位移非零即拖动"把抖动变成永远展不开菜单（FR-07 原文警告）；
  - 位置 = （贴哪一侧 + 纵向位置），落盘复用 T3-1 载体；恢复时 clamp 回当前屏内（屏幕尺寸变化 / 旋转后仍可找回）。
- **口径风险（已按 ADR-004 第 2/5 条化解）**：M0-A4/A5 的验收证据写的是窗口 `NOT_FOCUSABLE NOT_TOUCHABLE`
  + 覆盖区点击**穿透到游戏**。M3 落地为**两个窗口**：**标签窗保持 `NOT_TOUCHABLE`（恒穿透，A5 证据对它继续成立）**，
  另起一个**可触摸的手柄窗**（只吞自身矩形）。故无需改需求、无需改 ADR-004，只在
  `verification/README.md` 的 A5 行补一句"可触摸区域 = 手柄胶丸"的细化说明。
- **实现状态（2026-09-13，已完成；真机核对待 T3-6）**：
  - 几何与手势（纯逻辑）：`floating/FloatingPosition.kt`——`FloatingSide` / `FloatingPosition`（停靠侧 + **纵向比例**）/
    `FloatingLayout`（手柄贴边露出 40%、纵向还原 clamp、标签贴可见部分内侧并 clamp、拖动态留屏内）/
    `FloatingGesture.isDrag`（**按系统触摸滑动阈值**判拖动，不用"位移是否非零"）。数值全部来自运行时测量（红线 4）。
  - 位置持久化（ADR-006）：`floating/FloatingPositionCodec.kt`（`mm-floating` v1：`side` / `y-ratio` / `screen`）+
    `FloatingPositionStore.kt`（核心只吃 `File`；**缺失 / 损坏 → 回落默认 + 重写 + 原因回传写日志**；
    `loadOrNull` 供界面只读展示、不写盘；`reset` 供兜底入口）。
  - 窗口改造：`floating/FloatingWindow.kt` 重写为**标签窗（`NOT_TOUCHABLE`）+ 手柄窗（可触摸）**；
    手柄窗带 `FLAG_LAYOUT_NO_LIMITS`（允许部分移出屏幕）+ `FLAG_LAYOUT_IN_SCREEN`；
    拖动跟手（过程中 clamp 在屏内），**抬手才吸附**最近边缘并写盘；挂载前先手工测量、把初始位置算好再 `addView`
    （避免窗口在左上角闪一帧）；`FloatingScreen` 统一读屏幕尺寸（`currentWindowMetrics` / API 28~29 回退 `getRealSize`）。
  - 兜底入口：授权页新增「悬浮窗位置」卡（显示当前停靠侧 + 「重置到默认位置」）——
    即使在极端情况下手柄被拖到难以触达处，也能不依赖手柄自救（FR-07「始终可被找回」）。

## 已确认口径（2026-09-13，用户答复「按你的意见来」= 采纳 AI 建议）

1. **悬浮窗触摸口径**：FR-07 的「必须触摸穿透」按「**不得拦截游戏操作**」实现——紧凑手柄 / 菜单
   **只吞自身矩形**，其余区域照常穿透。代价是覆盖区内不再穿透到游戏（这正是"能点开菜单"的必然代价）。
   **落地后的更正（好消息）**：实现时发现 **ADR-004 第 2 / 5 条本就写明了这套两窗口设计**
   （"可触摸区域仅限收起态手柄（M3 引入交互后），其余部分（含状态标签）恒穿透" +
   "可交互的手柄 / 菜单使用独立的小窗口，与穿透标签分离"）→ 因此
   **`requirements.md` 与 ADR 都不需要修改**：FR-07 的「必须触摸穿透」由**标签窗**承接（恒 `NOT_TOUCHABLE`），
   交互由**另一个可触摸的手柄窗**承接。只在 `verification/README.md` 的 A5 行补一句口径细化说明即可。
2. **M3 的菜单边界**：菜单只**发出**「用户请求开始巡查」事件 + 日志（M4 消费）；「继续 / 跳过此项 / 停止巡查」
   三项 M3 **不出现**（巡查不可能在进行中），只在结构上预留入口。M3 全程对游戏**零注入点击**。
3. **「当前动作」展示位**：M3 只做字段与显示格式——有动作时显示「状态：X ／ <动作>」，无动作时只显示状态；
   动作由 M4 流程层写入。M3 不臆造动作内容。
4. **待命期状态恒显「未知」的可读性缺口**：**M3 不做低频全扫**——它是"显示"需求，但实现方式必然触碰搜索集合，
   而搜索集合直接决定 FR-01 的成本与灵敏度（M2-T2-5 刚把它收窄到 3 条）。留 **M5** 与性能优化一起评估；
   M3 悬浮窗如实显示「未知」（不粉饰、不造词），并在帮助文案里说明这是结构结果而非故障。
5. **贴边口径**：吸附**左右边缘**（竖屏使用场景）；按窗口宽度**硬性实现「露出约 40%」**（即 60% 移出屏幕）；
   纵向位置存取时 **clamp 在当前屏内**（换分辨率 / 旋转后仍可找回）。
   **落地时的细化（两条，手感请在 T3-6 真机上确认）**：
   ① 「露出 40%」适用于**收起态手柄**；**展开态**（菜单）临时把窗口完全收进屏内，否则菜单按钮会被屏幕边缘裁掉
   —— 展开本身是短暂操作，选完即收起恢复贴边；
   ② 纵向位置**存成占屏高的比例**（不是像素）：换分辨率后按比例还原仍落在相近的相对位置，
   存像素会被 clamp 到屏底、相对位置丢失。
   **已知局限（如实记录）**：手柄胶丸宽约 60dp，露出 40% ≈ **24dp 可见**，小于推荐的 48dp 触摸目标
   → 真机核对时若"不好点"，可把 `FloatingPosition.REVEAL_RATIO` 调大（一个常量，改动一处）。
6. **配置存储载体**：沿用「应用私有目录文本文件 + 纯函数编解码 + 临时文件重命名」→ 已定稿为
   [ADR-006](../../decisions/ADR-006-配置存储方式.md)（**状态：接受**）。
7. **「始终可被找回」的兜底**：**做**——在授权页加「悬浮窗位置」卡片（显示当前停靠侧 + 「重置到默认位置」），
   极端情况下（手柄被拖到不可触达处）用户仍能自救。随 T3-4 落地。

### T3-7 修订二（2026-09-14 用户真机反馈）：可见性缺陷 + 造型再定稿

- **缺陷（真机必现）**：装完看不到手柄与状态标签，**点一次「重置到默认位置」之后才出现**。
  - **根因（已定位）**：`show()` 里用 `measureSelf()` 手工测量窗口尺寸算初始位置，而收起态手柄是
    「空文字 + `MATCH_PARENT`」→ 在 `UNSPECIFIED` 规格下被测成 **0 宽** → 初始 x 被算成 `屏宽 - 0`
    → **整个手柄窗贴在屏幕外侧**（看不见也点不到）；挂载后的 `post { applyPositions() }` 又常抢在
    首帧布局之前跑（读到 0 宽直接 return），于是位置再没被纠正。
  - **修法**：① 收起态尺寸改用**常量**（`dp(28)` × `dp(64)`）直接写进 `addView` 的 `LayoutParams`，
    不依赖测量；② 两个窗口各挂 `addOnLayoutChangeListener`，**尺寸一变就重新落位**（比"post 一次"可靠）；
    ③ `place()` 在 x/y 未变时跳过一次 `updateViewLayout`（避免布局回调与位移互相触发）。
- **造型再定稿（用户口径）**：
  - 状态标签 → **半透明黑底 `0xB3000000` + 白字**（描一道 25% 白线，保证在黑底上能看出轮廓）；
  - 手柄 → **半透明琥珀黄 `0xE6FFC107`** + 深色箭头（`‹` 停靠右侧 / `›` 停靠左侧，**箭头对齐露在屏内的那一半**，
    否则会被屏幕边缘切掉）+ **更窄**：窗口 28dp × 64dp、一半在屏外 → 可见约 **14dp** 的窄竖条；
  - 手柄**始终贴边、拖不到屏幕中间**：拖动只沿边缘上下走（横向锁定），停靠侧不由拖动切换（要换边就重置）；
  - 展开菜单面板 → 参考 **vivo 手机游戏魔盒**：深色半透明 `0xE61C1C1C` 圆角面板 + 淡琥珀描边 +
    「图标 + 文案」功能行（本卡仍只有「开始巡查」一行，四组功能随 **T3-8** 落地）。
  - 需求侧无需再改：FR-07 的「吸附最近边缘」「紧凑」两条仍然成立（手柄总在边缘；窄竖条比原胶囊更小）。
- 验证：`FloatingPositionTest`（`snap` → `withTopY` 的用例改写）+ 全量 `:app:test -PfastTests` **344 例 0 失败** +
  `:app:assembleDebug` 通过 + 0 lint。
- **仍待真机确认**：可见约 14dp 的窄条是否够点（不够就调 `HANDLE_WIDTH_DP`）；箭头朝向与琥珀黄的观感。

| 底栏 | 「整体清空」（N ≥ 1 时） | 破坏性操作有确认弹窗（原有） |

**② 手势表**（阈值全部走 `ViewConfiguration` 或 dp 常量，无设备绑定数值）：

| 手势 | 触发条件 | 反馈 | 状态变化 | 反悔路径 |
| --- | --- | --- | --- | --- |
| **双击** | 两次点击间隔 ≤ `doubleTapTimeoutMillis`，各自位移 < `touchSlop` | 无 | 打开编辑页（三字段预填） | 「取消」 |
| **长按 + 上下拖** | 按住不动 ≥ `longPressTimeoutMillis`（其间位移不得超 `touchSlop`） | 行抬起（阴影 + 微放大）、每次换位一次轻震 | 拖动中只改**内存预览顺序**，**松手才落盘一次** | 拖动被系统打断 → 预览顺序丢弃、盘上未变 |
| **左滑** | 横向位移 > `touchSlop` 且 > 纵向位移；松手时越过「40dp 与行宽 25% 取大者」或甩速 ≥ 300dp/s | 行随手指左移，右侧露出红底「删除」 | 松手才弹**删除确认**（不是直接删） | 弹窗「取消」 |

**③ 冲突仲裁（设计师定稿，实现按此写）**：
1. 按下后**先纵向移动**超过 `touchSlop` → 判定为列表滚动（本行手势退出，不消费事件）；
2. 横滑一旦建立就**锁定**，中途不转滚动、不转拖动（"我在处理这一行"的语义）；滚动已开始时也不转横滑；
3. 长按到位后**纵向位移全部归拖动**，列表不再滚；拖动只取 y 分量（x 丢掉，留给横滑）；
4. **不做边缘自动滚动**：清单是"录一次用很久"的数据（预期十几条、一屏内可见 7 行以上），
   自动滚动要自己挂 `scrollBy` 循环并与"换位基准 index 重算"耦合，是本页最容易出玄学 bug 的一块；
   代价如实记录——**超过一屏必须分多次拖**，条目多到那个量级时再回头补（`§未决`）；
5. 只剩 1 条：双击照常编辑、左滑照常删（删完进空态）、长按可进拖动但**换位目标永远是自己且不落盘**；
6. 拖动/滑动被系统打断（来电、切后台、转屏）→ 预览顺序丢弃、不落盘；
7. **单击不做事**（用户口径是"双击进编辑"），提示行写清"双击"。

**④ 落盘口径**：拖动**松手才写一次盘**（`ServerList.moveTo(from, to)`）——逐次换位就写盘的话，
"写盘 → 重新读盘 → 重建列表"会把手指还按着的那一行顶掉（盘上文件是唯一数据源，ADR-006）；
写盘失败 / 拖动取消 → 界面自动回到盘上顺序（预览顺序清空）。

**⑤ 无障碍**：每行是**一个**可聚焦节点（`semantics(mergeDescendants = true)`），朗读串用中文逗号
（视觉摘要仍用「 · 」）；`customActions` 提供**编辑 / 上移 / 下移 / 删除**（端点不出现无效项）——
TalkBack 用户**不需要**做任何拖动或滑动。行高 72dp、页面按钮 ≥ 48dp；删除确认弹窗默认焦点在「取消」。

**⑥ 文案**（`strings.xml`）：新增 `server_gesture_hint`（"双击 = 编辑 ｜ 按住上下拖 = 排序 ｜ 往左滑 = 删除"）、
`server_delete_title/body/confirm`（标题带序号、正文含"区服名 · 角色名"辨识串 + 后果）、
`server_load_failed_hint`（损坏时说明"已保存的条目没被动过"）、`server_about`（说明入口）；
重写空态 `server_empty`（教怎么开始 + 讲三个手势）；旧文案里的"点这一条的「编辑」"改为"双击这一条"。

**⑦ 验收**（除原有 5 条外新增）：a) 双击某行 → 编辑页打开且三字段预填，直接保存 → 内容与顺序不变；
b) 单击某行 → 无任何变化；c) 长按拖动 → 行随手指走、松手后顺序落盘（杀进程重启仍是新顺序）；
d) 左滑过阈值 → 弹「删除第 N 条？」；未过阈值 → 回弹、无任何变化；e) 左滑纵向滚动互不干扰
（横滑时列表不动、纵滑时不弹窗）；f) 只剩 1 条时拖动不改变顺序也不写盘；g) 0 条时空态文案 +
「新增服务器」**同屏可见**（竖屏 360×792dp 与横屏 792×360dp 都不需要滚动）；
h) 全部行内按钮消失（页面上只剩 说明 / 返回 / 新增 / 整体清空 四个按钮）。

**⑧ 未决（留给用户拍板）**：a) 是否给"单击 = 编辑"做兜底（双击在本平台不如 iOS 常见，

**⑨ 实施纪律（本轮教训）**：真机 UI 核对**不再用 `wm size` 改屏幕尺寸**（会给用户手机留下

- **数据来源评估（结论：App 内维护为主，"从屏幕导入"作为助手放后面）**：
  1. OCR 在本项目是**尚未落地的前置能力**（ADR-003 只定了方向），批量识别还要处理滚动翻页、条目切分、
     区名与等级的对齐 —— 成本与不确定性都高；
  2. 这些名字会**直接用于点击定位**（红线 3：不唯一即停下），OCR 错一个字 = 找不到或点错别人，**代价不可逆**；
  3. 清单是"录一次用很久"的数据，手工维护成本很低；
  4. 折中（推荐并登记为后续任务）：**「从屏幕导入」助手**——停在服务器列表界面 → OCR 出候选 →

     同时保证名字与屏幕原文一致（比手打更准）。
  5. 等级 / 用户名**只作展示辨识**（帮用户认哪个是自己的小号），不参与定位。

### T3-9 列表改网格卡片（九轮，2026-09-14 用户口径「右侧留白太多，改成两列，卡片式布局如何?」）

**用户口径**：单列宽卡片在竖屏（可用宽 360dp）下**右侧空一大截** —— 内容只占左起约四分之一，
剩下四分之三都是卡片的空白；提改为**两列卡片式布局**。

**两个决策点（已与用户确认）**：

1. **列数 = 自适应**（按卡片最小宽换算，不在代码里写方向判断）：竖屏出 2 列、横屏出 4 列。
   代价（事先说明、用户接受）：竖屏每列约 160dp，**超长区服名会省略**（「微信256 天下无双」→「微信256 天下…」）；
   区服名是唯一定位字段，省略只影响列表可读性、不影响定位，但确实变差。
2. **卡片内排版 = 区服名独占一行**：窄卡片里把主信息竖过来，而不是继续横着排。

**改法**：

- 容器 `LazyColumn` → **`LazyVerticalGrid(GridCells.Fixed(cols))`**；列数由 `BoxWithConstraints` 的**可用宽**算：
  `cols = floor((maxWidth + gap) / (ServerCardMinWidth + gap))`，行高 / 列距 / 行距仍是 dp 常量（红线 4：不出现设备型号、
  分辨率、密度、坐标）。竖屏 328dp → 2 列 × 160dp；横屏 760dp → 4 列 × 184dp（同一条公式算出来的，不判断方向）。
- **卡片内三行**（行高 56 → **72dp**，行内左右留白 14 → **12dp**，行间距仍是 4dp）：
  - 第 1 行（11sp，**极弱**）：序号（primary）+ 平台区号（次级色）——**序号从卡片外的固定列移进卡片内**，
    不再白占 20dp 的独立列（窄卡片里 20dp 就是六分之一张卡）；
  - 第 2 行（14sp / Medium，**主角**）：区服名；
  - 第 3 行（11sp）：等级（primary）+ 角色名（次级色）；
  - 空字段仍不占位（三行里只渲染有内容的行，整体在卡片内垂直居中）。
- **拖动排序改二维网格落位**：横向位移按**列距**、纵向位移按**行距**分别折算成列 / 行步数 →
  目标格 `row * cols + col`，再夹进清单范围；换位后把**已经跨过的行与列**的位移分别减掉（手指下这张卡不跳）。
  纯函数落在 `ServerListGestures.dragTargetIndexInGrid`（连带原来的 `dragTargetIndex` 一起有单测）。
- **无障碍动作文案**：网格里「上移 / 下移」的说法不再对（右移一位并不是"下"）→ 改「**前移 / 后移**」。

**验收**：a) 竖屏 2 列、横屏 4 列，且**列数是算出来的**（同一份代码，无方向判断、无设备常量）；
b) 每张卡三行：小字「序号 + 平台区号」/ 大字区服名 / 小字「等级 + 角色名」，空字段不占位；
c) 双击编辑 / 左滑压出「删除」/ 长按拖动排序在网格里都仍可用 —— 拖动能**跨列也能跨行**换位，**松手才落盘**；
d) 排序后读到盘上的顺序 = 界面顺序（值不丢）。

- **现象**：每次授予采集权限后「允许真实点击」都被重置为未选中；而授权流程会把用户带到游戏，
  **没法在授权后再切回本体去开实点** → 变成"必须先建会话、再切回来开实点"，与真实操作顺序相反。
- **根因**：这是 T2-6 立的**安全边界 c**（采集会话建立 → 回演练，要求"每次会话由用户明确指示这次实点"）
  与授权流程的交互路径打架。
- **修法（最终定稿，2026-09-14 用户口径："无需新增开关"）**：**会话（重）建立不再重置运行方式**——
  `CaptureService` 不再调用 `ClickDispatch.enableDrill()`，只记一条日志。
  **安全边界由三条收敛为两条**：进程启动 = 演练；无障碍服务断开 / 被中断 = 回演练。
  （我先加了「建立采集会话后保留运行方式」开关，用户要求"直接不重置、不要开关" → **开关与
  `settings/AppPreferences` 已整体删除**，不留死代码。）
- **代价（如实记录）**：重新授权 / 系统回收重建会话都会沿用实点——用户不再被强制"每次确认"；
  授权页文案已相应改写（"运行方式会一直保留到你手动关闭"）。
- **未采纳的备选**：① 悬浮窗菜单里加「允许真实点击（本次会话）」——更贴近"我就在游戏这一侧"的直觉，
  但要给菜单加二次确认交互，**登记为可选后续**；② 让授权后自动切回本体——需要额外跳转，体验更差且
  越过系统授权流程。

**③ 手柄固定位置、不可拖动（2026-09-14 用户口径）**：
- 默认位置 = **右侧边缘、纵向三分之一**（`FloatingPosition.DEFAULT_Y_RATIO = 0.333333`；
  取 6 位小数是为了"写盘 → 读盘"逐位相等，不会每次挂载都判成"位置变了"）；
- **宽度加宽三分之一**：14dp → **19dp**（可见约 9dp）；
- **移除手柄拖动**：位置固定，触摸只剩「单击展开 / 收起菜单」（`FloatingPosition.withTopY` 与其用例一并删除）；
  状态标签仍可自由拖动。

**④ 可见性缺陷第二次修复（"又要重置位置才看得见"）**：
- 上一轮改成常量尺寸后仍会复现 → 问题不在测量，而在**摆放时用的屏幕尺寸不是窗口最终所在的坐标系**
  （挂载瞬间可能还是转屏前的尺寸）：两个窗口会被一起摆到屏幕外，只能靠一次"重置位置 / 重新挂载"回来。
- 修法：**注册 `DisplayManager.DisplayListener`**，屏幕尺寸 / 方向一变就重新落位（转屏、`wm size`、
  折叠屏展开都覆盖）；`hide()` 时注销。
- **新增落位日志（排障用）**：`悬浮窗落位: 屏 WxH ｜ 手柄 (x,y) wxh ｜ 标签 (x,y) wxh`，
  内容变化才写一次——下次若还看不见，一行日志就能判断是不是屏幕尺寸用错了。

**⑤ 手柄位置不再持久化 + 菜单独立成窗（2026-09-14 第五轮）**：
- **用户报的 bug**："手柄出现在屏幕右侧**下方**三分之一"（要求的是上方三分之一）。
  **真因不是坐标算错**：屏幕尺寸、比例换算都正确，是**旧位置文件里的 `handle-y-ratio` 一直在生效**——
  手柄虽然已不可拖动，位置却还在持久化，于是"新默认值"永远只在**文件不存在**时才生效，
  要用户点一次「重置到默认位置」才回头。**这类 bug 的根因是模型错了：手柄位置已经不是用户数据。**
- **修法（模型收窄）**：`FloatingPositions` 只存**状态标签**（`handle` 变成指向 `FloatingPosition.DEFAULT` 的常量访问器）；
  位置文件格式升 **v3**（去掉 `handle-*`，保留 `label-*` / `screen`）；
  v1 / v2 文件读入时**忽略其中手柄取值**、保留标签位置，并顺手重写为 v3（`needsRewrite`；
  原因带回调用方写日志）。用户**不需要再点重置**。
- **交互：展开后手柄不消失**（用户口径）：菜单从"手柄的展开形态"改为**独立窗口**
  （手柄窗 / 菜单窗 / 状态标签窗，共三个）——手柄的尺寸、背景、位置在整个展开过程中保持不变，
  顺手消掉了"展开态改窗口尺寸"这一整类时序坑。
- **点非菜单区域收起**：菜单窗带 `FLAG_WATCH_OUTSIDE_TOUCH`，`ACTION_OUTSIDE` → 收起；
  触点在**手柄**范围内时不在此处收起（交给手柄自己的单击切换，避免"先收起再被切回来"）。
- **菜单几何（纯函数，可单测）**：`FloatingLayout.menuX`（完全在屏内 + 避开手柄露出的那一条）、
  `FloatingLayout.menuY`（与手柄中心对齐 + clamp 在屏内）。

**⑥ 手柄可见区与触摸区分离（2026-09-14 第六轮）**：
- 用户口径："缩短 1/4 手柄宽度" + "点击很难被触发"。
- **放弃"一半移出屏幕"**：那个技巧只做到了"露一半少挡视线"，但**移出去的部分收不到触摸**
  ——等于要求用户点中那 7dp。改为**窗口完全在屏内**：可见条贴边（由子视图定位，7×32dp），
  窗口其余部分是**透明触摸区**（向屏内 16dp、上下各 6dp → 窗口 23×44dp）。
- **手感补充**：`systemGestureExclusionRects` 声明手势排除区（API 29+，尽力而为）——
  手柄贴屏幕边缘，正是"侧滑返回"起手区，系统可能先一步吃掉触摸。
- **代价如实记录**（进 FR-07 口径修订三）：手柄占住的触摸区比看得见的宽，屏幕右缘这条 23×44dp 不再传给游戏。
- **连带修正**：可见条 7dp 宽时圆角半径必须 ≤ 可见宽度的一半（写死 9dp 会画成畸形）；
  `menuX` 的避让参数从"窗口宽"改为"**可见条宽**"（菜单只需避开看得见的那一条）。

### UI 架构重构（2026-09-15，UX 全局审核后启动）

> 来源：用户「页面架构太乱、很多东西挤在一起，不同页面应统一操作逻辑，重构模块与页面分布，
> 采用导航栏 / tab 等安卓布局控件，让 UX 决定用什么」。UX agent 读完项目后出方案，**三项已由用户拍板**。

**① 导航选型（UX 定）**：4 个一级页 = **运行 / 巡查 / 清单 / 设置**；
**竖屏 `NavigationBar`（80dp）/ 横屏 `NavigationRail`（80dp 宽）**，判据 = 可用宽 ≥ 600dp（Material 断点令牌，非设备常量）。
理由：横屏可用高只有 360dp，底栏吃掉 80dp 后清单页只剩 1 行卡片；Rail 在竖屏又会把内容宽挤到 280dp。
**不新增依赖**（手写约 30 行的二选一），不加 `androidx.navigation`（目的地少、层级固定、无深链）。
返回栈：切一级页 = 替换并清二级栈；二级页返回 = 回所属一级页；一级页返回 = 回「运行」，已在「运行」则退出。

**② 统一列表行契约**（点按 = 编辑 / 左滑露出红按钮 = 删除 / 长按拖动 = 排序 / 新增在操作行右端 /
整体清空在底栏 + 二次确认 / 每行一个语义节点 + `customActions`）；编辑表单一律**全屏编辑页**（横屏限宽 0.5 靠左）。

**③ 页面归属**：授权页 → **「运行」页的一块**（未齐展开、齐了折叠成一行）+ 采集会话 / 常驻守护 / 运行方式三块；
识别标定页 → **「设置」页**；清单页 = 服务器 + 好友（**竖屏 Tab / 横屏左右两栏**）。
