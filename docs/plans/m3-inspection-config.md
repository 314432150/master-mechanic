## 范围边界

- **做**：
  - 巡查配置的**数据模型 + 校验 + 持久化 + 配置界面**（FR-03 全部条目）；
  - 悬浮窗**触摸口径修订**（收起态手柄必须可触摸才能"单击展开"）、**拖动判定**（按系统触摸滑动阈值）、
    **贴边吸附**、**位置持久化**、**展开态紧凑菜单**、**菜单动作出口**（发出"用户请求开始巡查"事件）、
    **收起时机**（成功收起 / 失败保持展开并显示原因）；
  - 「当前动作」展示位（字段与显示格式；内容由 M4 流程层写入）。
- **不做**：
  - **巡查主流程（FR-04）/ 中断恢复（FR-05）/ 巡查记录（FR-06）**——属 M4。M3 的菜单只把"用户请求"发出去，
    **不产生任何游戏点击**（红线 2：M3 不新增点击来源）；
  - 区服名 / 好友名的**名称定位与唯一性判定**（属 M4，`requirements.md` §4-4 / 红线 3）；
  - 性能达标（NFR-01 / NFR-02 未达标项移交 M5）；FR-08 加固（帧流静默停止检测等，后续里程碑）。

### T3-4 悬浮窗触摸口径修订 + 拖动 / 贴边 / 位置持久化

- 目标：把 `FloatingWindow` 由「整窗不可触摸 + 固定右上角」改为「**紧凑可触摸手柄** + 拖动跟手 + 抬手贴边 +
  位置持久化」。
- 验收：C3（紧凑 + 自身矩形外不拦截游戏触摸）/ C4（按系统触摸滑动阈值判拖动）/ C5（贴边吸附约 40% 露出 +
  位置持久化 + 尺寸变化后可找回）/ C8（非前台整窗移除回归）。
- 证据：拖动判定与贴边几何的**纯逻辑单测**（阈值判定 / 吸附计算 / clamp 与找回）+ 真机核对
  （用户执行：拖到四角 / 贴边 / 杀进程重启看位置 / 覆盖区点击穿透对比——复用 M0-T0-5 的"游戏静音图标切换"手法）。
- 实现要点（待确认）：
  - `WindowManager.LayoutParams` 去掉 `FLAG_NOT_TOUCHABLE`（保留 `FLAG_NOT_FOCUSABLE`），
    即**只有手柄自身矩形吞触摸**——这正是 FR-07「紧凑到只包住内容」的用意；
  - 拖动阈值取**系统 API**（`ViewConfiguration` 的触摸滑动阈值）的运行时值，不写常数（红线 4）；
  - 触摸事件到"是拖动还是单击"的判定放在**抬手时**裁决（超过阈值 = 拖动、未超过 = 单击展开），
    避免"位移非零即拖动"把抖动变成永远展不开菜单（FR-07 原文警告）；
  - 位置 = （贴哪一侧 + 纵向位置），落盘复用 T3-1 载体；恢复时 clamp 回当前屏内（屏幕尺寸变化 / 旋转后仍可找回）。
- **口径风险（已按 ADR-004 第 2/5 条化解）**：M0-A4/A5 的验收证据写的是窗口 `NOT_FOCUSABLE NOT_TOUCHABLE`
  + 覆盖区点击**穿透到游戏**。M3 落地为**两个窗口**：**标签窗保持 `NOT_TOUCHABLE`（恒穿透，A5 证据对它继续成立）**，
  另起一个**可触摸的手柄窗**（只吞自身矩形）。故无需改需求、无需改 ADR-004，只在
  `verification/README.md` 的 A5 行补一句"可触摸区域 = 手柄胶丸"的细化说明。
- **实现状态（2026-09-13，已完成；真机核对待 T3-6）**：
  - 几何与手势（纯逻辑）：`floating/FloatingPosition.kt`——`FloatingSide` / `FloatingPosition`（停靠侧 + **纵向比例**）/
    `FloatingLayout`（手柄贴边露出 40%、纵向还原 clamp、标签贴可见部分内侧并 clamp、拖动态留屏内）/
    `FloatingGesture.isDrag`（**按系统触摸滑动阈值**判拖动，不用"位移是否非零"）。数值全部来自运行时测量（红线 4）。
  - 位置持久化（ADR-006）：`floating/FloatingPositionCodec.kt`（`mm-floating` v1：`side` / `y-ratio` / `screen`）+
    `FloatingPositionStore.kt`（核心只吃 `File`；**缺失 / 损坏 → 回落默认 + 重写 + 原因回传写日志**；
    `loadOrNull` 供界面只读展示、不写盘；`reset` 供兜底入口）。
  - 窗口改造：`floating/FloatingWindow.kt` 重写为**标签窗（`NOT_TOUCHABLE`）+ 手柄窗（可触摸）**；
    手柄窗带 `FLAG_LAYOUT_NO_LIMITS`（允许部分移出屏幕）+ `FLAG_LAYOUT_IN_SCREEN`；
    拖动跟手（过程中 clamp 在屏内），**抬手才吸附**最近边缘并写盘；挂载前先手工测量、把初始位置算好再 `addView`
    （避免窗口在左上角闪一帧）；`FloatingScreen` 统一读屏幕尺寸（`currentWindowMetrics` / API 28~29 回退 `getRealSize`）。
  - 兜底入口：授权页新增「悬浮窗位置」卡（显示当前停靠侧 + 「重置到默认位置」）——
    即使在极端情况下手柄被拖到难以触达处，也能不依赖手柄自救（FR-07「始终可被找回」）。

### T3-5 悬浮窗展开菜单 + 菜单动作出口 + 收起时机

- 目标：单击展开**紧凑菜单**（文案随模式变化）；菜单动作经统一出口发出**事件**（M4 消费），
  成功即收起、失败保持展开并显示原因。
- 验收：C6（单击只展开不执行 / 紧凑 / 文案随模式）/ C7（成功收起、失败保持展开并说明原因）/
  C10（动作经 `ClickDispatch` 且来源 `FLOATING_MENU`，不新增来源）。
- 证据：展开-收起状态机与"成功/失败 → 收起/保持"的**纯逻辑单测** + 真机 UI 核对（用户执行）。
- 实现要点（待确认）：
  - 菜单项按模式显示：**待命 = 「开始巡查」**；「继续 / 跳过此项 / 停止巡查」属巡查进行中（M4），
    M3 只在结构上预留（不制造"点了没反应"的哑按钮）；
  - 点「开始巡查」在 M3 = **发出"用户请求开始巡查"事件 + 日志**（M4 接）；**不产生游戏点击**；
  - 展开态同样要紧凑（展开即吞掉其矩形内的触摸 → 操作完成后**立刻收起**恢复穿透）；
  - 失败时保持展开并显示原因，文案复用"不静默失败"的既有风格（§1.3 / FR-08）。
- **实现状态（2026-09-13，已完成；真机核对待 T3-6）**：
  - 菜单与手势：手柄窗单击（位移未超阈值）展开 / 收起；**展开本身不执行任何操作**（FR-07 原文）；
    展开态临时完全进屏，选完即收起；展开时会清掉上一次的失败原因（每次尝试都是新的一次）。

### T3-7 修订二（2026-09-14 用户真机反馈）：可见性缺陷 + 造型再定稿

- **缺陷（真机必现）**：装完看不到手柄与状态标签，**点一次「重置到默认位置」之后才出现**。
  - **根因（已定位）**：`show()` 里用 `measureSelf()` 手工测量窗口尺寸算初始位置，而收起态手柄是
    「空文字 + `MATCH_PARENT`」→ 在 `UNSPECIFIED` 规格下被测成 **0 宽** → 初始 x 被算成 `屏宽 - 0`
    → **整个手柄窗贴在屏幕外侧**（看不见也点不到）；挂载后的 `post { applyPositions() }` 又常抢在
    首帧布局之前跑（读到 0 宽直接 return），于是位置再没被纠正。
  - **修法**：① 收起态尺寸改用**常量**（`dp(28)` × `dp(64)`）直接写进 `addView` 的 `LayoutParams`，
    不依赖测量；② 两个窗口各挂 `addOnLayoutChangeListener`，**尺寸一变就重新落位**（比"post 一次"可靠）；
    ③ `place()` 在 x/y 未变时跳过一次 `updateViewLayout`（避免布局回调与位移互相触发）。

### T3-9 服务器清单（FR-10：数据模型 + 界面 + 数据来源评估）

- 需求锚点：**FR-10**（`requirements.md` 新增节；FR-09 已被「前台判定」占用）。FR-07「换号」行加注「清单见 FR-10」。
- 目标：App 内维护一份**有序**的服务器清单，供换号时挑选目标（T3-8 的三级菜单消费）。
- 数据模型：`ServerEntry(区服名称, 角色名, 等级)` 的**有序**清单 —— 有序是"按顺序切下一个"的前提；
  **只有区服名称参与定位**，角色名与等级**只用于辨识**（不参与定位，红线 3）。
  **等级存文本**：游戏里形如「Lv.50」「王者」并不统一，编数值规则既无必要、也会拒收合法输入。
- 格式：`servers/list.txt`，标记 `mm-servers` v1，行 `item=<区服名称>|<角色名>|<等级>`；
  三个字段**总是写出**（空字段靠"分隔符照写"定位）→ 不存在"空字段被省略 / 挤位"的歧义；
  严格拒收（格式标记 / 版本 / 未知键 / 分隔符不足 2 个 / 区服名为空 / 字段含分隔符或换行），消息带行号（ADR-006）。
- 界面：授权页新增入口 → **第 4 页**：列表（条数 / 空态 / 解析失败原因 + 「清空重建」）+ 新增 / 编辑 / 上移下移 / 删除 / 整体清空。
- 验收：
  1. 授权页有「服务器清单」入口并进入该页；空清单、解析失败都有明确呈现（不静默变空）；
  2. 增 / 删 / 改 / 调序 / 整体清空全部可用，且**每次编辑都落盘**（盘上文件是唯一数据源，写入失败不改界面并提示）；
  3. 区服名称为空、或任一字段含「|」/ 换行 → 保存时**明确提示**，不静默丢弃；
  4. 重启后清单仍在；文件被改坏 → 报错 + 可清空重建；
  5. 既有能力不回退（`-PfastTests` 全绿 + `assembleDebug` 通过）。
- 证据方式：模型 / 编解码 / 存储单测（JVM，25 例）+ 建包 + **真机界面核对**
  （截图：入口、空态、全屏编辑页三字段、空区服名的提示）。
- **实现状态（2026-09-14 完成；真机界面已核对）**：
  - 代码：`servers/ServerList.kt`、`servers/ServerListCodec.kt`、`servers/ServerListStore.kt`、`ui/ServerListScreen.kt`；
    改动 `MainActivity.kt`（四页导航）、`ui/AuthorizationScreen.kt`（入口）、`res/values/strings.xml`（+34 条）。
  - 验证：`ServerListTest` 11 + `ServerListCodecTest` 9 + `ServerListStoreTest` 5 = **25 例新增**；
    `:app:test -PfastTests` **374 例 0 失败** + `:app:assembleDebug` 通过 + 0 lint。
  - **真机发现（坑，值得记）**：三字段的 `AlertDialog` 在**横屏**下装不下 —— 本机横屏可用高度只有 **360dp**
    （3168×1440 @ 640dpi），Material3 会把溢出内容塞进内部滚动区并加一条分割线，**第三个字段（等级）看起来像不存在**
    （已截图取证）。改为**全屏编辑页**（`Dialog(usePlatformDefaultWidth = false)` + 铺满 `Surface`，与标定工作台同一做法），
    底部一行「取消 / 保存」，横竖屏都完整可见。
  - **未覆盖（如实记录）**：真机 UI 的"填完保存 → 列表出现条目 → 重启仍在"未做自动化点击
    （中文输入要靠软键盘，盲点不可靠）——该路径的落盘 / 读盘由 25 例单测覆盖（与巡查配置同一实现），
    **请用户自己点一次确认**；三级菜单消费该清单属 T3-8。
- **数据来源评估（结论：App 内维护为主，"从屏幕导入"作为助手放后面）**：
  1. OCR 在本项目是**尚未落地的前置能力**（ADR-003 只定了方向），批量识别还要处理滚动翻页、条目切分、
     区名与等级的对齐 —— 成本与不确定性都高；
  2. 这些名字会**直接用于点击定位**（红线 3：不唯一即停下），OCR 错一个字 = 找不到或点错别人，**代价不可逆**；

### 追加需求（二轮，2026-09-14）：手柄再缩半 + 实点开关与授权流程

**① 手柄尺寸与透明度**（用户口径："高度 / 宽度都缩减为目前的一半，改为半透明色"）：
- 窗口 28×64dp → **14×32dp**（一半在屏外 → **可见约 7dp**）；
- 填充 `0xE6FFC107`（90%）→ **`0xB3FFC107`（70%，更透）**；
- 收起态**不再写字/箭头**（7dp 宽放不下，写了也会被屏幕边缘切掉）——形状本身即"把手"，
  展开态表头仍显示 `≡`。
- **手感风险（如实记录）**：可见 7dp 极小，可能点不中。两个旋钮：`FloatingPosition.REVEAL_RATIO`
  （1.0 = 整条都在屏内，可见 14dp）或 `HANDLE_WIDTH_DP`。

**② 实点模式与采集授权流程冲突（用户报的"操作逻辑"缺陷）**：
- **现象**：每次授予采集权限后「允许真实点击」都被重置为未选中；而授权流程会把用户带到游戏，
  **没法在授权后再切回本体去开实点** → 变成"必须先建会话、再切回来开实点"，与真实操作顺序相反。
- **根因**：这是 T2-6 立的**安全边界 c**（采集会话建立 → 回演练，要求"每次会话由用户明确指示这次实点"）
  与授权流程的交互路径打架。
- **修法（最终定稿，2026-09-14 用户口径："无需新增开关"）**：**会话（重）建立不再重置运行方式**——
  `CaptureService` 不再调用 `ClickDispatch.enableDrill()`，只记一条日志。
  **安全边界由三条收敛为两条**：进程启动 = 演练；无障碍服务断开 / 被中断 = 回演练。
  （我先加了「建立采集会话后保留运行方式」开关，用户要求"直接不重置、不要开关" → **开关与
  `settings/AppPreferences` 已整体删除**，不留死代码。）
- **代价（如实记录）**：重新授权 / 系统回收重建会话都会沿用实点——用户不再被强制"每次确认"；
  授权页文案已相应改写（"运行方式会一直保留到你手动关闭"）。
- **未采纳的备选**：① 悬浮窗菜单里加「允许真实点击（本次会话）」——更贴近"我就在游戏这一侧"的直觉，
  但要给菜单加二次确认交互，**登记为可选后续**；② 让授权后自动切回本体——需要额外跳转，体验更差且
  越过系统授权流程。

**③ 手柄固定位置、不可拖动（2026-09-14 用户口径）**：
- 默认位置 = **右侧边缘、纵向三分之一**（`FloatingPosition.DEFAULT_Y_RATIO = 0.333333`；
  取 6 位小数是为了"写盘 → 读盘"逐位相等，不会每次挂载都判成"位置变了"）；
- **宽度加宽三分之一**：14dp → **19dp**（可见约 9dp）；
- **移除手柄拖动**：位置固定，触摸只剩「单击展开 / 收起菜单」（`FloatingPosition.withTopY` 与其用例一并删除）；
  状态标签仍可自由拖动。

**④ 可见性缺陷第二次修复（"又要重置位置才看得见"）**：
- 上一轮改成常量尺寸后仍会复现 → 问题不在测量，而在**摆放时用的屏幕尺寸不是窗口最终所在的坐标系**
  （挂载瞬间可能还是转屏前的尺寸）：两个窗口会被一起摆到屏幕外，只能靠一次"重置位置 / 重新挂载"回来。
- 修法：**注册 `DisplayManager.DisplayListener`**，屏幕尺寸 / 方向一变就重新落位（转屏、`wm size`、
  折叠屏展开都覆盖）；`hide()` 时注销。
- **新增落位日志（排障用）**：`悬浮窗落位: 屏 WxH ｜ 手柄 (x,y) wxh ｜ 标签 (x,y) wxh`，
  内容变化才写一次——下次若还看不见，一行日志就能判断是不是屏幕尺寸用错了。

**⑤ 手柄位置不再持久化 + 菜单独立成窗（2026-09-14 第五轮）**：
- **用户报的 bug**："手柄出现在屏幕右侧**下方**三分之一"（要求的是上方三分之一）。
  **真因不是坐标算错**：屏幕尺寸、比例换算都正确，是**旧位置文件里的 `handle-y-ratio` 一直在生效**——
  手柄虽然已不可拖动，位置却还在持久化，于是"新默认值"永远只在**文件不存在**时才生效，
  要用户点一次「重置到默认位置」才回头。**这类 bug 的根因是模型错了：手柄位置已经不是用户数据。**
- **修法（模型收窄）**：`FloatingPositions` 只存**状态标签**（`handle` 变成指向 `FloatingPosition.DEFAULT` 的常量访问器）；
  位置文件格式升 **v3**（去掉 `handle-*`，保留 `label-*` / `screen`）；
  v1 / v2 文件读入时**忽略其中手柄取值**、保留标签位置，并顺手重写为 v3（`needsRewrite`；
  原因带回调用方写日志）。用户**不需要再点重置**。
- **交互：展开后手柄不消失**（用户口径）：菜单从"手柄的展开形态"改为**独立窗口**
  （手柄窗 / 菜单窗 / 状态标签窗，共三个）——手柄的尺寸、背景、位置在整个展开过程中保持不变，
  顺手消掉了"展开态改窗口尺寸"这一整类时序坑。
- **点非菜单区域收起**：菜单窗带 `FLAG_WATCH_OUTSIDE_TOUCH`，`ACTION_OUTSIDE` → 收起；
  触点在**手柄**范围内时不在此处收起（交给手柄自己的单击切换，避免"先收起再被切回来"）。
- **菜单几何（纯函数，可单测）**：`FloatingLayout.menuX`（完全在屏内 + 避开手柄露出的那一条）、
  `FloatingLayout.menuY`（与手柄中心对齐 + clamp 在屏内）。

**⑥ 手柄可见区与触摸区分离（2026-09-14 第六轮）**：
- 用户口径："缩短 1/4 手柄宽度" + "点击很难被触发"。
- **放弃"一半移出屏幕"**：那个技巧只做到了"露一半少挡视线"，但**移出去的部分收不到触摸**
  ——等于要求用户点中那 7dp。改为**窗口完全在屏内**：可见条贴边（由子视图定位，7×32dp），
  窗口其余部分是**透明触摸区**（向屏内 16dp、上下各 6dp → 窗口 23×44dp）。
- **手感补充**：`systemGestureExclusionRects` 声明手势排除区（API 29+，尽力而为）——
  手柄贴屏幕边缘，正是"侧滑返回"起手区，系统可能先一步吃掉触摸。
- **代价如实记录**（进 FR-07 口径修订三）：手柄占住的触摸区比看得见的宽，屏幕右缘这条 23×44dp 不再传给游戏。
- **连带修正**：可见条 7dp 宽时圆角半径必须 ≤ 可见宽度的一半（写死 9dp 会画成畸形）；
  `menuX` 的避让参数从"窗口宽"改为"**可见条宽**"（菜单只需避开看得见的那一条）。
