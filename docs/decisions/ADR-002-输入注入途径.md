# ADR-002：输入注入途径

| 项 | 内容 |
| --- | --- |
| 日期 | 2026-09-11 |
| 状态 | 接受 |
| 关联需求 | §3.2、§4、NFR-05、NFR-06、红线 2、红线 6 |

## 背景

一切点击必须由程序下发，且只发生在四种合法来源下（红线 2）；相邻点击间隔 ≥300ms 必须由统一实现点保障，不依赖调用方自觉（红线 6）；每次点击必须可审计（NFR-05）。需要在非 root 前提下选择输入注入途径，并同时确定"间隔 ≥300ms 的唯一实现点"。

## 决策

采用**无障碍手势注入（AccessibilityService.dispatchGesture，API 24+）**作为唯一注入通道。

**唯一实现点：执行层的"点击转发器"（单一组件）。** 所有调用方（FR-01、巡查主流程、悬浮窗菜单；FR-02 已于 2026-09-13 移除）只能经它下发点击，全部约束由它承担：

1. **门禁**：非前台（ADR-005 信号）或状态未知 → 拒绝下发并记录，绝不试探（红线 1、§4-2）；等待期间门禁在真正下发前复核一次；
2. **间隔**：以单调时钟计量，前一次手势**完成**到下一次手势**开始**不低于 300ms，不足则等待——该口径比"开始到开始"更保守，兼容 NFR-06 的任何解释；
3. **串行**：同一时刻只允许一个手势在途；派发失败或被打断（onCancelled）一律按"点击未完成"处理，交由步骤验证失败路径，不盲重试（红线 5）；
4. **审计与来源**：每次下发必须携带判定记录 ID 与来源枚举（四类合法来源之一），构成 NFR-05 的点击审计链。

其余实现约束：点击以短行程 stroke 实现；坐标一律来自识别判定结果；服务配置声明手势能力（canPerformGestures）。

## 备选方案

| 方案 | 放弃理由 |
| --- | --- |
| 无障碍节点 performAction（按节点点击） | 游戏画面为自绘引擎渲染，节点树中不存在游戏内的按钮控件，无法给出可靠坐标；且 §4-4 要求按识别结果定位 |
| adb shell input 类方案 | 依赖与电脑连接，普通用户场景不可用 |
| root 注入（injectInputEvent 等） | 违反 §1.3 非 root 前提 |
| 插桩测试类注入 | 需要调试签名与测试环境，非交付形态 |

## 后果

- 注入能力完全依赖无障碍服务：服务不可用 = 不能点击；与 ADR-004、ADR-005 共用同一服务，整体按"不可用即停"处理（宁可停住，不可乱点）。
- 手势可能被系统打断（取消回调），流程必须把"点击未生效"当作正常失败来处理——与 FR-04"动作后必须验证"机制天然一致。
- 未来的长按/滑动（如 FR-04 第 4 步的滚动查找）同样经该转发器下发，自动继承串行与间隔约束。
- 本方案不设计任何"隐蔽注入"；与游戏交互的手段限定在无障碍与屏幕采集的公开能力内（§1.3）。

## 补记：坐标换算归转发器（2026-09-20，真机缺陷驱动）

**背景**：请求里带的是**运行帧坐标**（识别判定结果），而 `dispatchGesture` 要的是**屏幕坐标**。
两者只在"帧 == 屏幕"的会话（横画布）恰好相等；竖画布会话下帧 1440×3168、屏幕 3168×1440，
原样下发直接落到屏幕外——真机实录"点了毫无反应"（连点 8 次，见 `progress.md` 第 85 条）。

**决策（补进上面第 4 条"审计与来源"同层）**：

1. **换算的唯一实现点是点击转发器**（`ClickForwarder`）：它是唯一出口，调用方各自换算迟早漏一个。
   请求仍只带帧坐标（红线 4/ADR-002 原口径不变：坐标必须来自识别判定结果）；
2. **换算公式**（`ClickGeometry`，纯逻辑）：`屏幕 =（帧 − 画面区左上）× 屏幕尺寸 / 画面区尺寸`，
   画面区取自识别层同一几何口径（`CanvasGeometry`）；三方几何（标定帧 / 运行帧 / 屏幕）任一缺失 →
   **不换算**（`IDENTITY` 原样下发，与修复前一致），**绝不猜**（红线 3/7）；
3. **越界即拒**：换算后的落点不在显示区域内 → 拒绝下发（`ClickDenyReason.OUT_OF_SCREEN`，留痕）。
   门禁顺序变为：演练 → 非前台 → 状态未知 → **落点越界** → 串行 → 间隔；
4. **审计记两套坐标**（帧点 + 屏幕点）：真机上"点歪了"必须能区分**识别定位错**与**换算错**。

**后果**：`ClickForwarder` 的职责由"门禁 / 间隔 / 串行 / 审计"四件变五件（+ 坐标换算）；
这条约束是**硬性**的——任何绕过它直接调 `GestureInjector` 的实现都算破坏 ADR-002 的"唯一实现点"。

## 补记二：输入拟人化（2026-09-21，用户口径）

**背景**：用户提出"所有识别到的坐标换算成屏幕坐标后加细微随机偏移，点击从按下到弹起也加随机偏移，
尽量模拟真人操作习惯"。

**术语（先对齐叫法）**：这类做法叫 **输入拟人化 / 输入抖动**（human-like input / input jitter）；
它对抗的是游戏的**反自动化检测**（anti-bot / anti-cheat）——"反爬"是网页爬虫语境的说法。
机器人特征里最容易被抓的两条：**永远落在同一个像素**、**永远同一时长同一条轨迹**。

**决策**：

1. **抽象成专门模块** `action/InputJitter.kt`（纯逻辑、`Random` 可注入）；
2. **落点抖动**：由 `ClickForwarder` 在**换算成屏幕坐标之后**施加，半径默认 **±3 屏幕像素**，
   并**夹回显示区域内**——不抖的两种情形：落点已判越界、或屏幕尺寸未知（"不知道就不猜"）；
3. **按压抖动**：`AccessibilityGestureInjector` 的短行程长度 / 方向 / 按压时长随机（40~80ms、1~3px、0~2π），
   取代原先写死的"1px 斜线 + 50ms"；
4. **单一施加点**：落点抖动在转发层（唯一下发口）→ 三条来源（FR-01 / 跑号 / 悬浮窗菜单）自动全覆盖，
   不存在"哪条路径忘了抖"。

**与「不设计任何隐蔽注入」的界分（重要）**：本补记**不改变**上面第 4 条——
注入途径仍是无障碍 `dispatchGesture` 这一条公开能力，也不隐瞒"程序在点击"这件事；
变的只是**落点与节奏的取值分布**。**不做的**：伪造触摸来源 / 隐藏无障碍服务 / 绕过系统提示，
这些仍在禁止之列。

**对既有不变量的一处放宽（如实记录）**：§5-4「同一输入序列 → 完全相同结果」**对点击落点与时长不再成立**
（这正是拟人化的目的）；**识别与判定链路仍然完全确定性**。抖动序列可由种子复现（单测用固定种子）。

**幅度受控（红线 3 / 7）**：抖动半径只有 3 屏幕像素（3168 宽上约千分之一），目标是"不总是同一个像素"，
**不是**"点得偏一点"；越界者夹回屏内，因此不会因为抖动点到屏幕外或点出锚点。
