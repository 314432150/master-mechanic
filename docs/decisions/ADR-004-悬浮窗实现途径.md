# ADR-004：悬浮窗实现途径

| 项 | 内容 |
| --- | --- |
| 日期 | 2026-09-11 |
| 状态 | 接受 |
| 关联需求 | FR-07、§5-6、红线 1 |

## 背景

FR-07 要求：常驻半透明标签、**必须触摸穿透**；仅游戏前台时可见、非前台完全消失；紧凑到只包住内容。M0 只做"壳"（可见性 + 触摸穿透 + 收起态手柄），拖动/贴边/菜单在 M3。需要选择窗口类型与挂载方式。

## 决策

采用**无障碍悬浮窗（TYPE_ACCESSIBILITY_OVERLAY，API 22+）**，由无障碍服务挂载；不申请"显示在其他应用上层"（SYSTEM_ALERT_WINDOW）。

1. **挂载**：从无障碍服务上下文创建窗口，不引入额外授权，授权矩阵保持最短。
2. **穿透**：展示标签使用"不可触摸 + 不可聚焦"标志，永不拦截触摸——包括其覆盖区域内的游戏操作与自身注入的点击。可触摸区域仅限收起态手柄（M3 引入交互后），其余部分（含状态标签）恒穿透；M0 无交互，整窗不可触摸。
3. **可见性**：仅当 ADR-005 的前台信号为"目标应用在前台"时显示；非前台时完全消失（不可见且不占任何触摸）；回前台以收起态重建。
4. **尺寸**：窗口严格紧凑只包内容。
5. **M3 扩展预留**：可交互的手柄/菜单使用独立的小窗口（可触摸），与穿透标签分离——触摸只吸附在手柄范围内，标签区域始终穿透。
6. **收起规则**：默认收起；操作成功结束后立即收起，失败时保持展开并显示原因（FR-07 收起时机）。

选择该类型的核心理由：系统对触摸穿透的"不受信任遮挡"限制（Android 12+）将无障碍窗口列为**可信窗口**，穿透不受窗口不透明度约束；而普通应用悬浮窗（TYPE_APPLICATION_OVERLAY）不受信任，穿透受约 0.8 不透明度阈值约束，一旦外观调整越线就会静默拦截触摸，直接破坏 A5（触摸穿透）。

## 备选方案

| 方案 | 放弃理由 |
| --- | --- |
| TYPE_APPLICATION_OVERLAY + SYSTEM_ALERT_WINDOW | 多一项特殊授权，增加静默失败面（FR-08）；非可信窗口，穿透受不透明度阈值约束，外观变化即可静默拦截触摸 |
| Activity 内嵌视图 | 无法在游戏之上显示，不满足常驻展示 |
| Toast / 通知替代 | 不满足常驻、紧凑与后续交互要求 |
| 系统级窗口类型（TYPE_SYSTEM_ALERT 等） | 第三方应用不可用 |

## 后果

- 悬浮窗生命周期与无障碍服务绑定：服务不可用时悬浮窗不存在——与"服务不可用即按非前台/整体停止"的处理一致（红线 1）。
- 悬浮窗像素会进入系统采集画面（ADR-001）："悬浮窗状态不影响识别结果"（§5-6）由识别层保证，M1 标定需包含悬浮窗开/关对照样本。
- 不同厂商对无障碍悬浮窗的行为可能有差异：A4、A5 的真机核对是验收门槛；若个别设备验证失败，以新 ADR 切换为 APPLICATION_OVERLAY 方案（编号不复用）。
