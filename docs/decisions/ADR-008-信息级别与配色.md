# ADR-008：信息级别与配色

| 项 | 内容 |
| --- | --- |
| 日期 | 2026-10-01 |
| 状态 | 接受 |
| 关联需求 | FR-07（悬浮窗）、§5-6、FR-08（不静默失败） |

## 背景

程序要给用户"说话"的地方越来越多：悬浮窗底部信息条、顶部状态标签、菜单状态行、授权页、
标定页提示。2026-10-01 之前**只有一条红色信息位**（`FloatingWindow.REASON_COLOR`），
什么话都往里塞 ⇒ 一句回执（"提示位置已重置"）也显示成红色，读起来像出了故障。

用户当天给出两条口径：

1. **"提示类信息不应该使用红色"** —— 红是"要你处理"的信号，用在"只是告知"的话上会误导；
2. 把提示条改成中性白后**"不够明显"** —— 诊断：问题不在亮度，而在**色相没差别**
   （菜单功能行本来就是一整片白字，白 80% 只是"更白的白"，眼睛不会把它拎出来）。

⇒ 需要一套**按信息级别分配颜色**的约定，让"说什么"和"什么颜色"一一对应，一次定死、以后照抄。

## 决策

### 一、六个级别（判据：**用户需要动手吗？**）

| 级别 | 含义 | **深底**（悬浮窗 / 标定夜底） | **亮底**（Compose 页面） |
| --- | --- | --- | --- |
| **L1 失败 / 被拒** | 当前做不了，**需要你动手** | 亮红 `#FF8A80` | Material `colorScheme.error` |
| **L2 警示 / 隐患** | 现在能用，**但有风险** | 琥珀 `#FFD54F` | 深琥珀 `#8A5A00` |
| **L3 提示 / 回执** | **只是告知**（你做完了一件事 / 当前状态） | 浅青蓝 `#80D8FF` | 深青蓝 `#00697C` |
| **L4 完成 / 成功** | 一件事**正面收尾** | 浅绿 `#69F0AE` | 深绿 `#1B7A3E` |
| **L5 普通内容** | 功能行 / 正文 / 可点项 | 白 `#FFFFFF` | `colorScheme.onSurface` |
| **L6 状态 / 次要** | 报状态（不可点、弱化一档） | 白 70% `#B3FFFFFF` | `colorScheme.onSurfaceVariant` |

⚠ **深底与亮底是"一对"值，不是同一个值**（照抄标定页 `ON_DARK_ERROR` 那条教训：亮色主题的
`error` 是深红，在黑底上读不出来）。上表两列必须成对使用。

### 二、落地位置（现有常量与 ADR 的对应）

| 位置 | 用到的级别 | 常量 / 代码 |
| --- | --- | --- |
| 悬浮窗底部信息条（失败） | L1 | `FloatingWindow.REASON_COLOR` |
| 悬浮窗底部信息条（提示） | L3 | `FloatingWindow.NOTICE_COLOR` |
| 悬浮窗菜单状态行（中止 / 暂停） | L1 | `FloatingWindow.REASON_COLOR`（需要你决策 ⇒ L1） |
| 悬浮窗菜单功能行 / 图标 | L5 | `MENU_TEXT_COLOR` / `MENU_GLYPH_COLOR`（琥珀是**装饰**，不是级别） |
| 悬浮窗状态行 | L6 | `STATUS_COLOR` |
| 授权页"缺授权" | L1 | `colorScheme.error` |
| 授权页"守护在跑但通知被关" | L2 | `Warning40` |
| 标定页错误（预览加载失败） | L1 | `ON_DARK_ERROR` |
| 标定页次要文字 | L6 | `ON_DARK_SECONDARY` |
| 标定页**框选角色色** | —— | **不属本表**（见第四条） |

### 三、五条使用规则

1. **一个位置只说一件事**：L1 与 L3 **互斥**（同一条信息位）——挂提示清失败、挂失败清提示；
   否则用户会同时看到"刚才那件事失败了"和"这件事已经做完"，不知道哪句是当前状态。
2. **颜色跟着语义走，不跟着"想更醒目"走**：同一句话永远同一个级别；嫌不显眼要改的是**级别判据或措辞**，
   不是随手换个颜色。
3. **级别数量克制**：日常只有 **L1 / L3 / L5 / L6** 在用；L2 / L4 **确有对应语义时**才用，
   不要为了"好看"造第三档提示色。
4. **领域色不参与**：标定页的「标志红 / 锚点青 / 未定琥珀」是**框选角色的领域语义**，
   与信息级别无关 ⇒ 各管各的（同一屏里出现两种红，含义不同是正常的）。
5. **不依赖颜色**：措辞本身必须把话说清（色觉障碍者不看颜色也知道发生了什么）；
   颜色只用来**加速识别**，不作为唯一载体。

### 四、不用纯饱和色

`#FF0000` / `#00FF00` 这类纯饱和色**不用**：深底上刺眼、11sp 小字的边缘发虚。
上表取的是 Material 的 200/300 档（浅而亮）与 600/700 档（深而稳）。

## 备选方案

| 方案 | 放弃理由 |
| --- | --- |
| 全部保持白色，靠字重 / 底色区分 | 用户实测"不够明显"：一片白字里加粗一行，仍不成为"一块信息"（无色相差别） |
| 只用红 / 白两档（改前现状） | 回执被迫用红 ⇒ 用户读成故障（这次改动的起因） |
| 用绿表示"成功"、黄表示"警告"、蓝表示"信息"——即本表，但把 L2/L4 也铺开用 | 采纳本表；但**不主动**给每个新消息找级别，只有语义明确时才用（见规则 3） |
| 每个页面各定一套色 | 同一种"失败"在不同页面颜色不同 ⇒ 用户学不会、我们每处都要重新讨论 |

## 后果

- **收益**：颜色成了可检索的语义（"红字 = 我得去处理"），用户不用读完整句话就知道要不要停手；
  新加消息时只需回答一个问题（**用户需要动手吗？**）就能定色，不必每次重新讨论。
- **代价 / 约束**：
  - 深底 / 亮底两套值必须成对维护 ⇒ **新增一条消息时要同时想好它出现在哪种衬底上**；
  - 级别判据（"需要动手吗"）带主观性 ⇒ 边界情况以用户口径为准（例：点「停止」但没在跑 ⇒ **L3**，
    因为它只是告知；起点不成立导致点不动 ⇒ **L1**，因为它拦下了用户想做的事）；
  - L2 / L4 目前**只有值、没有使用者**（L2 仅授权页；L4 尚未使用）⇒ 用之前先确认语义真的对得上。
- 与红线的关系：不涉及七条红线；本 ADR 约束的是**表现层**，不动采集 / 识别 / 注入任何口径。

## 修订

- 2026-10-01（同日）：L3 由"中性白 `#CCFFFFFF`"改为"浅青蓝 `#80D8FF`"（用户口径"中性白不够明显"，
  根因是**色相无差别**而非亮度不足）。
