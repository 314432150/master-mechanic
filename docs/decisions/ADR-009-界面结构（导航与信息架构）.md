# ADR-009：界面结构（导航与信息架构）

| 项 | 内容 |
| --- | --- |
| 日期 | 2026-10-01 |
| 状态 | **提议**（待用户确认；确认后改「接受」并同步 `architecture.md` / `progress.md`） |
| 关联需求 | FR-07（悬浮窗与操作菜单）、FR-03 作废后的「拜访规则」预设、FR-04（跑号主流程）、FR-05（中断与恢复）、§2.1 界面清单；**不触及七条红线**（约束的是表现层） |

## 背景

2026-10-01 用户口径：**"app 里的功能布局繁杂混乱，需要按功能重新设计布局结构，包含导航栏、抽屉弹窗等各安卓结构框架组件都可以用上。同时，精简冗长的提示文案。"**

现状（2026-10-01 盘点）：

| 症状 | 事实 |
| --- | --- |
| **没有导航** | 全 App 1 个 Activity（`MainActivity`），用 `var screen by rememberSaveable` + `when(screen)` 切 4 个页面；**没有** Navigation 框架、顶栏、底栏、抽屉、Tab、Sheet |
| **功能全挤在一页** | 首页（授权页）既是"授权状态检查"又是**唯一的功能入口**（3 个按钮：识别标定 / 服务器 / 好友）；真正的执行（换号 / 拜访 / 换号+拜访）与**拜访规则编辑只在悬浮窗**，App 里没有 |
| **同名能力两个入口、职责不清** | 「导入服务器」在悬浮窗（只能新增/补全），完整增删改在 App 清单页；用户无从知道该去哪 |
| **文案过长** | `strings.xml` 454 条，最长一条 **≈640 字**（标定页使用说明），另有 ≈490 / 230 / 160 / 120 / 110 字多档；**≈50 条 `patrol_*` 已是死文案**（无任何引用，随 `screen==2` 页面移除遗留） |
| **单文件过大** | 标定页 `ui/CalibrationScreen.kt` **173.7 KB**（页面 + 全屏工作台 + 3 个对话框都在里面） |

## 决策

### 一、信息架构：**4 个一级目的地 + 4 个抽屉目的地**

| 层级 | 目的地 | 放什么（一句话） |
| --- | --- | --- |
| **底部导航（一级）** | **运行** | 现在能不能跑 / 跑到哪了 + 发起「换号 / 拜访 / 换号+拜访」+ 停止 / 继续 |
| | **规则** | **拜访规则**预设编辑（区服策略：顺序轮换 / 固定区服；好友选择）+「保存并开始」 |
| | **清单** | 两个 Tab：**区服清单** / **好友清单**（增删改、排序、改名同步） |
| | **标定** | 样本帧采集 + 产物清单/参数 + 进入**全屏标定工作台** |
| **抽屉（系统级）** | **授权与权限** | 无障碍 / 屏幕采集 / 常驻守护 / 通知四项状态与一键授予 |
| | **诊断** | 画面是否在来（帧率/停更）、当前识别画面与分数、单帧耗时、日志入口 |
| | **设置** | 自动关弹窗暂停/恢复、悬浮窗提示位置重置、退出 App |
| | **帮助 / 关于** | 术语与流程说明、长文案的"为什么"（见决策三） |

**首次启动**：关键授权缺失 ⇒ **自动进「授权」页**（引导式，一屏四步）；授权齐全后默认落在**「运行」**。

### 二、结构组件：用标准件，不自研

| 用途 | 组件 |
| --- | --- |
| 页面切换 / 返回栈 | `androidx.navigation:navigation-compose`（`NavHost` + `navController`）替代裸 `when(screen)` |
| 骨架 | `Scaffold` + `TopAppBar`（一级页 = 抽屉图标 + 标题 + 溢出菜单；二级页 = 返回箭头） |
| 一级导航 | `NavigationBar`（4 项） |
| 系统级入口 | `ModalNavigationDrawer` |
| 清单两个 Tab | `SecondaryTabRow` + 横向分页 |
| 行内操作 / 说明 | `ModalBottomSheet`（取代现在动辄一屏的 `AlertDialog`） |
| 长说明 | 折叠区（默认收起，展开为 Sheet）：**首屏永远只有 1 行** |
| 撤销 / 回执 | 沿用现有 `SnackbarHost` |

### 三、文案规则（六条，可验收）

1. **首屏只说"下一步做什么"**：超过 **60 字**的说明一律改「**1 行要点** + 「查看用法」折叠」，**默认收起**；
2. **字段级 hint 取代段落**：清单/表单的长副标题拆进**占位符、表头小字、字段说明**；
3. **两句话原则**：错误 / 提示只说 **①发生了什么 ②你要做什么**；"为什么会这样"挪进「帮助/关于」或日志；
4. **删死文案**：`strings.xml` 中无引用的 `patrol_*`（≈50 条）删除，并加单测防复发；
5. **术语统一**：一律用 `docs/glossary.md` 的词（禁止另造词）；
6. **颜色分级照旧**：文案级别与配色仍按 `ADR-008`（L1~L6），本 ADR 不改颜色口径。

### 四、明确不动的部分

- **悬浮窗继续做"游戏内遥控器"**（跑号时人在游戏里，不该被逼回 App）；App 内的「运行/规则」页是**同一能力的完整版**，不是替代；
- **两个入口的分工写死**：悬浮窗 = 快捷执行与最小编辑（预设只能改草稿并直接开始）；App = 完整编辑与数据维护（冲突时以 App 为准）；
- **七条红线、采集/识别/注入口径、产物格式**一律不动。

## 备选方案

| 方案 | 放弃理由 |
| --- | --- |
| 保留 `when(screen)`，自己手写底栏/抽屉 | 返回栈、状态保存、二级页返回、深链都要自己实现一遍 ⇒ 花更多代码换来更差的一致性 |
| 只加底部导航栏、不动信息架构 | 治不了根因：**功能与入口混在一页**（授权页当首页当日志当功能入口），文案照旧无处安放 |
| 全部功能收进抽屉（无底栏） | 高频的「运行」要"打开抽屉再点"两步；且抽屉对 4 个以上一级目的地的发现性差 |
| 把标定 / 清单也搬进悬浮窗 | 编辑型界面（表单、拖动排序、全屏框选）在悬浮窗里做不出来；悬浮窗尺寸受限 |
| 引入第三方 UI 库 / Compose Multiplatform | 无收益：需求是"结构清晰 + 文案短"，Material3 标准件够用，还多一层维护成本 |

## 后果

- **收益**：一屏一件事（每页只回答一个问题）；任意页面 ≤2 次点击可达；长文案有了归宿（折叠 / 帮助页）；
  文案精简从"看心情"变成**可验收的量化目标**（见 `plans/m5-ui-restructure.md` 的 V1~V6）。
- **代价 / 约束（如实记录）**：
  - **新增依赖** `navigation-compose`（需按 `AGENTS.md` 先征得用户确认）；
  - **文案压缩会丢信息**："为什么会这样"要挪到帮助页 / 日志 ⇒ 用户可能多一次点击；
  - **悬浮窗与 App 出现"同一能力的两个入口"** ⇒ 必须靠上面那条分工约定维持一致（改预设字段时两处都要跟）；
  - **标定页要拆文件**（173.7 KB ⇒ 3~4 个文件，纯搬迁不改行为），迁移期容易产生冲突；
  - **无障碍要求落到结构上**：一级导航要有 `contentDescription`、触控目标 ≥48dp、TalkBack 顺序正确（新增验收项 V6）。
- 与红线的关系：不涉及任何一条；本 ADR 只约束**表现层与信息架构**。
